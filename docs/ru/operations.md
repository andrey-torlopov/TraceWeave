# Управление установкой

*[English](../en/operations.md)*

Команды выполняются из того же checkout и с тем же runtime, что bootstrap. `./traceweave.sh --help` показывает фактические флаги. CLI проверяет Docker/Compose и сериализует изменяющие операции файловой блокировкой `runtime/operation.lock`. Второй update/backup/restore не начинает работу параллельно с первым. Записи `operation.json` и `journal.jsonl` сохраняются вне контейнеров; их не удаляют для обхода сбоя.

## Основные команды

| Команда | Действие |
| --- | --- |
| `./traceweave.sh start` | Запустить и проверить db/gateway, затем backend/frontend текущего закреплённого релиза; проверить версии/схему/health, открыть gateway. Прерванная операция блокирует start. |
| `./traceweave.sh stop` | Включить и проверить заглушку, дождаться остановки backend до 180 секунд, затем остановить frontend/gateway/db. Volumes остаются. |
| `./traceweave.sh restart` | Включить заглушку, остановить backend, перезапустить frontend, вернуть backend и проверить готовность. PostgreSQL и gateway остаются. |
| `./traceweave.sh status` | Показать URL, release ID, фазу, имена volumes и Compose status. |
| `./traceweave.sh logs` | Последние 100 строк backend/frontend/gateway/db. |
| `./traceweave.sh logs backend db` | Последние 100 строк только выбранных сервисов; другие имена отклоняются. |
| `./traceweave.sh maintenance on` | Включить заглушку без остановки backend; завершить через проверяемый `resume`. Прямой `maintenance off` отсутствует. |
| `./traceweave.sh resume` | Продолжить либо проверить завершение прерванной операции, если её фаза допускает это. |

Читать логи можно без изменения установки, но логи и runtime относятся к приватным данным оператора. Не публикуйте их целиком. `start` не запускает миграции неизвестного релиза и не скачивает новую версию приложения по плавающему tag. Для смены версии служит [update](releases.md).

## Обслуживание и остановка

Gateway независимо отвечает HTML для страницы и JSON `service_maintenance` для `/api/*` и `/health/*`, статусом 503, `Retry-After: 15`, `Cache-Control: no-store`. `/release.json` остаётся доступным для проверки версии. Gateway не повторяет мутации. Открытая вкладка сохраняет редактор и pending запрос; пользователь разбирает его исход или повторяет точное тело с прежним operationId. Обновление страницы производится только по явному действию пользователя после обработки черновиков.

Остановка backend считается штатной только при отсутствии running/OOMKilled и коде выхода 0 либо 143. Эта проверка выполняется также перед rollback и пересозданием backend при configure-mail. SIGKILL, OOM или иной код оставляют незавершённую фазу и закрытый доступ; это не успешное обновление. При незавершённой фазе `start` отказывает и не открывает gateway. Проверьте `status`, логи и состояние незавершённых загрузок/экспортов; после устранения причины используйте соответствующий путь восстановления.

Если вызван `stop` во время незавершённой операции, состояние становится `stopped-interrupted` и содержит прежнюю фазу. `resume` возвращается к ней, а не превращает сбой в штатный start. Не используйте `docker compose down`, `down -v`, `docker volume prune` или удаление журналов как процедуру обновления. [Docker volumes сохраняют данные независимо от контейнеров](https://docs.docker.com/engine/storage/volumes/).

## Аккаунты

Первый аккаунт создаётся bootstrap. Прямая команда `account create` предназначена только для первой учётной записи пустой установки; при существующем владельце она отказывает и не меняет данные. Для обычного первого запуска используйте bootstrap. Команда для отдельного первоначального административного шага:

```sh
printf 'Email аккаунта: '
IFS= read -r TW_ACCOUNT_EMAIL
printf 'Имя первого аккаунта: '
IFS= read -r TW_ACCOUNT_NAME
./traceweave.sh account create --email "$TW_ACCOUNT_EMAIL" --name "$TW_ACCOUNT_NAME"
```

Для изменения пароля выбранного существующего аккаунта выполните отдельную операцию:

```sh
printf 'Email существующего аккаунта для смены пароля: '
IFS= read -r TW_ACCOUNT_EMAIL
./traceweave.sh account reset-password --email "$TW_ACCOUNT_EMAIL"
```

Пароли вводятся скрыто в TTY. Скрипты не выводят действующий пароль, не имеют стандартного пароля и не присоединяют исследования к другому owner. Account CLI использует одноразовый owner-контейнер выбранного backend image. Дополнительные аккаунты создаются через разрешённую публичную регистрацию с HTTPS, SMTP и подтверждением email; локальный HTTP bootstrap не включает регистрацию. SMTP/регистрация настраиваются через [configure-mail](installation.md#https-на-сервере).

При выходе или смене аккаунта в другой вкладке frontend блокирует старую очередь. Для продолжения того же черновика нужно войти в прежний аккаунт; явная смена пользователя требует разбора черновиков. Backend сравнивает expected account header с фактической сессией для защищённых запросов; browser storage не даёт полномочий на данные другого пользователя.

## Приватный offline backup

```sh
./traceweave.sh backup
```

CLI включает заглушку, подтверждает 503, штатно останавливает backend и сохраняет согласованный offline snapshot. PostgreSQL остаётся запущенным. Ops удерживает advisory lock `8476004`; backup отказывается работать при активном backend/изменяющем CLI и прерывает `pg_dump` при потере lease. После успешной проверки backend запускается, проверяется и доступ открывается. CLI печатает конкретный путь `runtime/backups/NAME`.

Перед `pg_dump` ops измеряет фактический размер БД через `pg_database_size(current_database())` и суммарный размер сохраняемых оригиналов. Требуемое свободное место в каталоге backup рассчитывается как `requiredBytes = 2 × databaseBytes + originalBytes + 64 × 1024 × 1024`. При недостатке места dump не начинается. Для команды update контроллер дополнительно проверяет 1 GiB в runtime ещё до начала обслуживания; это не заменяет расчёт ops перед backup.

Копия содержит `database.dump` в custom format, оригиналы `blobs/` и `manifest.json`: release images/версии, PostgreSQL version, положительный целочисленный `databaseBytes`, историю миграций, SHA-256 dump и каждого оригинала, проверенные ссылки базы на файлы. `databaseBytes` фиксирует размер БД на момент backup, а не размер сжатого dump. Служебные `staging/exports` не архивируются как завершённые пользовательские результаты. [PostgreSQL custom dump](https://www.postgresql.org/docs/18/backup-dump.html).

В копии есть данные всех аккаунтов, их password hashes, история и текущие DB-сессии/токены. Это административная информация. Каталог приватный, файлы `0600`; он не должен попадать в Git, публичный webroot или обычный пользовательский экспорт. Копия внутри того же Docker-хоста не защищает от потери самого хоста.

Перенесите конкретный завершённый каталог на отдельное защищённое хранилище, сохранив структуру, права и контрольные суммы. Секреты и конфигурацию установки сохраняют отдельно с ограниченным доступом: `runtime/secrets/`, `installation.json`, выбранный `release.json` и нужные release manifests. Не включайте их в публичный пакет. Перед переносом убедитесь, что backup завершён (`status` показывает `ready` с его ID), а не содержит только незавершённый dump. Для внешнего хранилища используйте шифрование и отдельный доступ оператора; verify restore выполняется на синтетической/отдельной установке.

CLI принимает backup из своего `runtime/backups/`, а не произвольный внешний абсолютный путь: аргумент `--backup` используется как имя последнего компонента. Внешнюю копию сначала возвращают целиком в этот приватный каталог под исходным именем, без symlink и специальных файлов. Не накладывайте её на существующую копию с тем же ID. Проверка hashes выполняется перед restore и при восстановлении.

## Restore в новые volumes

Выберите имя существующей проверенной копии, показанное backup:

```sh
printf 'Имя каталога backup внутри runtime/backups/: '
IFS= read -r TW_BACKUP_NAME
./traceweave.sh restore --backup "$TW_BACKUP_NAME"
```

CLI проверяет manifest/dump/оригиналы, наличие образов релиза копии и запрашивает подтверждение. Далее он включает обслуживание, штатно останавливает backend и снимает **safety backup текущего состояния**: записи после выбранной старой копии должны оставаться восстанавливаемыми. Создаются новые database/files volumes с суффиксом `-restore-...`; существующие volumes не очищаются и не удаляются.

Перед восстановлением ops требует положительный целочисленный `databaseBytes` в manifest, проверяет dump/оригиналы и рассчитывает тот же бюджет `requiredBytes = 2 × databaseBytes + originalBytes + 64 × 1024 × 1024` по выбранной копии. Свободное место проверяется отдельно на новом originals mount `/data` и database volume, подключённом к ops read-only как `/database-capacity`. Этот mount нужен для проверки capacity: БД восстанавливается через PostgreSQL, ops не записывает файлы database volume напрямую. При недостатке места на любом из двух mounts восстановление dump и blobs не начинается.

В новые пустые БД и originals storage восстанавливаются dump и blobs. Ops проверяет hashes, ссылки и миграции, отзывает все сессии и account tokens. Незавершённые uploads/imports и transient exports переводятся в interrupted/failed; экспорт нужно создать заново. После проверки образов, схемы и сервисов установка переключается на новые volumes и релиз копии. Старые volumes и safety backup остаются. Пользователи заново входят в аккаунты.

Требуется место для выбранной копии, safety backup и новых volumes. Capacity preflight не резервирует место: оператор также учитывает совместное размещение volumes на одном хранилище и рост данных. Restore не является merge старой копии с поздними изменениями. Оператор заранее решает, как обработать данные, появившиеся после даты выбранной копии.

## Прерванная операция

Сначала выполните `status` и прочитайте последние логи. Заглушка должна оставаться включённой, пока не прошла проверка. Не запускайте второй update/backup/restore поверх незавершённой операции.

| Фаза | Доступный путь |
| --- | --- |
| `bootstrap-*` | `resume --email ... --name ...` либо повторный bootstrap с прежним manifest/origin. Пароли снова требуют TTY, существующая учётная запись сохраняется. |
| `update-*` | `resume` использует `update-source.json` и `pending-release.json`: запускает db/gateway под проверенной заглушкой до чтения истории схемы, затем продолжает update. Альтернатива — совместимый `rollback`. После изменения схемы потребуется restore pre-update backup или исправляющий релиз. |
| `rollback-*` | После устранения причины повторите совместимый `rollback`; обычный start не завершает прерванный откат. |
| `backup-*`, `restart-*`, `stopping`, `maintenance-*` | `resume` запускает и проверяет db/gateway, затем приложения текущего релиза и открывает gateway. Неудавшаяся копия не объявляется успешно завершённой. |
| `restore-*` | Автоматический `resume` запрещён. Используйте `restore-revert` для возврата сохранённой исходной установки, либо отдельную ручную проверку кандидата оператором. |
| `stopped-interrupted` | `resume` восстанавливает прежнюю фазу и применяет её правила. |

```sh
./traceweave.sh resume
./traceweave.sh restore-revert
```

Эти команды являются альтернативами по таблице. `restore-revert` возвращает database/files volumes и release из `restore-old-installation.json` / `restore-old-release.json`, проверяет их и открывает сервис. Кандидат restore сохраняется для анализа. После успешного restore эта команда также означает явный отказ от выбранного восстановленного состояния; новые записи кандидата не сливаются со старой установкой.

Update, rollback, resume и restore требуют подтверждения `YES` в TTY. `--yes` лишь пропускает этот вопрос; он не отменяет guards, проверки схемы и hashes. Используйте его только в заранее разобранной автоматизации или проверяемой синтетической установке. Для SMTP/пароля аккаунта этот флаг не отменяет скрытый ввод.
