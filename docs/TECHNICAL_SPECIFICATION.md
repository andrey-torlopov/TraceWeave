## 0. Как читать и исполнять это ТЗ

> **Принятое изменение от 2026-10-08:** [CR-E0-002 — macOS и отложенные плагины](change-requests/CR-E0-002-macos-and-plugin-deferral.md) имеет приоритет над упоминаниями обязательной Linux-приёмки и plugin-протокола ниже. Текущая приёмка — macOS; Linux/Docker и AC-59/60 отложены. Сборки и установка необходимых инструментов разрешены владельцем.

TraceWeave опирается на OSINT-анализатор [Flowsint](https://github.com/reconurge/flowsint) как на основной визуальный и функциональный референс, особенно в части самостоятельного развёртывания сервиса. Предоставленные скриншоты задают ориентиры интерфейса; функциональные сценарии и способ эксплуатации адаптируются к требованиям этого документа. Обязательный объём TraceWeave определяется этим ТЗ; роль Flowsint уточнена в разделе 3.3. [S17]

- **P0 / MUST** — обязательная функциональность первой рабочей версии. Релиз не принимается без её реализации и проверки.
- **P1 / SHOULD** — следующий этап; не входит в приёмку первой версии.
- **P2 / FUTURE** — архитектурное направление. В P0 запрещено имитировать его готовность неработающими кнопками.
- **ADR** — короткая запись об архитектурном решении: проблема, рассмотренные варианты, выбранный вариант, последствия, проверка.
- **AC** — проверяемый сценарий приёмки.

**Правило для агентов:** сначала прочитать разделы 1–5, 12–16 и 24–29. Затем выполнять только назначенный пакет работ. Нельзя самостоятельно сокращать P0, менять модель хранения, подменять сервер localStorage или выбирать другой стек из личных предпочтений.

## 1. Назначение и результат

### 1.1. Основная задача

Разработать локально разворачиваемое веб-приложение для ручного исследования: хранения материалов, описания сущностей, установления связей, формирования гипотез и документирования выводов.

Пользователь должен иметь возможность создать исследование, разместить документы-сущности на графе, связать их подписанными линиями, прикрепить исходные материалы, объединить связанные элементы в группы и подготовить отчёт.

**Главная единица данных — документ-узел. Главная форма навигации — интерактивный граф.** Граф не заменяет содержимое документов, а показывает отношения между ними.

### 1.2. Ожидаемый законченный результат P0

Работающий продукт, в котором пользователь без изменения исходного кода:

1. Запускает сервер, входит в интерфейс и создаёт исследование.
2. Создаёт персону, телефон, место, заметки и другие узлы.
3. Редактирует документы, добавляет атрибуты и загружает материалы.
4. Соединяет узлы, указывает смысл и степень проверенности связей.
5. Открывает несколько карточек одновременно, пользуется поиском и инспектором.
6. Группирует узлы, сворачивает группу и восстанавливает исходный граф.
7. Записывает выводы со ссылками на основания.
8. Получает Markdown-отчёт и переносимый архив исследования.
9. Перезапускает приложение и продолжает работу без потери подтверждённо сохранённых данных.

### 1.3. Что приложение не должно утверждать

Наличие линии на графе не доказывает наличие реальной связи. Совпадение имени, телефона, адреса или изображения не означает идентичность объектов. Статус «подтверждено пользователем» — оценка автора исследования, а не результат автоматической верификации.

Приложение должно различать материал, утверждение, гипотезу и вывод. Оно не должно автоматически повышать достоверность данных из-за того, что они импортированы, получены плагином или имеют много связей.

## 2. Зафиксированные решения и устранение неоднозначностей

Эти решения приняты для получения непротиворечивого реализуемого P0. В редакции 1.1 по запросу владельца подтверждён Swift со стабильным Vapor, выбран React для интерактивного UI и принято использование PostgreSQL вместо SQLite. Оставшиеся технические решения перечислены отдельно в разделе 2.3.

| ID | Вопрос | Решение для P0 |
|---|---|---|
| D-01 | Backend | Swift 6.x + стабильная ветка Vapor 4; проверенный стабильный релиз на дату этой редакции — 4.122.2. Vapor 5 beta/alpha не использовать. Совместимость полного набора зависимостей подтвердить на E0 [S18] |
| D-02 | Интерактивный frontend | TypeScript + React, сборка через Vite; браузерная SPA, HTML/CSS для представления. Собранные ассеты отдаёт Vapor, дополнительный production-сервер Node.js не требуется; обоснование в разделе 2.1 |
| D-03 | Библиотека графа | Открытое ядро React Flow, пакет `@xyflow/react`. Пользовательские узлы и рёбра реализовать самостоятельно; платные примеры не обязательны |
| D-04 | «Узел — определённый тип данных» | Разделить смысловой тип узла и формат его вложений. Персона может одновременно содержать Markdown, изображение, аудио и видео |
| D-05 | Карточка открыта до крестика, но справа сменяется при выборе | Это два независимых представления: открытая карточка на графе и один правый инспектор. Выбор другого узла меняет инспектор, но не закрывает карточки |
| D-06 | Группировка | Группа — отдельный документ-контейнер. В P0 один уровень вложенности, без групп внутри групп. Обычный узел входит максимум в одну группу |
| D-07 | Исследование и несколько холстов | В P0 одно исследование содержит один граф. Несколько холстов одного исследования — P1, без копирования документов |
| D-08 | Пользователи | Один локальный пользователь-владелец; вход обязателен. Регистрация, команды и совместное редактирование не входят в P0 |
| D-09 | Хранение | PostgreSQL — единственная основная БД P0; Fluent + `FluentPostgresDriver`. Бинарные оригиналы — в локальной файловой системе вне webroot. PostgreSQL является обязательной локальной службой; браузер не является основным хранилищем |
| D-10 | Плагины | В P0 — версионированный файловый контракт, схемы и тестовые примеры. Установка и запуск произвольного кода не входят в P0 |
| D-11 | Отчёт | Ручная структура и детерминированная сборка Markdown. Генерация выводов нейросетью не входит в P0 |
| D-12 | Docker | P0 должен быть подготовлен к контейнеризации. Готовый Dockerfile/Compose — отдельный P1, не условие работоспособности локального P0 |
| D-13 | Obsidian | Переносимый Markdown-экспорт. Прямая интеграция, плагин Obsidian и двусторонняя синхронизация не входят в P0 |
| D-14 | Интернет | Для работы с уже загруженными данными внешний интернет не требуется. Сбор данных с сайтов, поиск людей и внешние API не запускаются автоматически |
| D-15 | Карта | Место хранит координаты и описание. Интерактивная географическая карта — P1; наличие геолокации не означает обязательную интеграцию с картографическим сервисом |

**Обоснование стека:** Swift/Vapor соответствует выбранному владельцем backend-языку; Fluent официально поддерживает PostgreSQL и рекомендует этот драйвер. React Flow предоставляет пользовательские узлы, связи и базовые механизмы группирования. Это проектный выбор по требованиям и поддерживаемости, а не утверждение об универсальном превосходстве языка или framework. [S01–S06]

**Версии:** на E0 проверить совместимость Swift 6.x, Vapor 4, Fluent/PostgreSQL-драйвера, PostgreSQL, Node.js, TypeScript, React, React Flow и Vite. Vapor 4.122.2 — исходный проверенный стабильный релиз; более свежий стабильный релиз ветки 4 допускается после проверки совместимости. Для PostgreSQL выбрать поддерживаемую стабильную major-версию; исходный кандидат — 18, точный minor-релиз и версии `pg_dump`/`pg_restore` фиксируются на E0. Зафиксировать весь проверенный набор в `docs/toolchain.md`, lock-файлах и CI. Не использовать `latest`, nightly, alpha, beta, RC или плавающие Docker-теги в воспроизводимой сборке. Номера релизов проверять по официальным источникам; факт публикации не заменяет проверку совместимости. [S18, S21]

### 2.1. Выбор понятного UI-стека

**Решение: React + TypeScript + React Flow + Vite.** Критерий простоты для TraceWeave — объём собственного кода для карточек, связей, групп, панелей и общего черновика документа, а также понятность границ между ними.

| Подход | Применимость и компромисс | Решение |
|---|---|---|
| React + React Flow | Готовые механизмы графа и пользовательских компонентов; документация предлагает Vite для запуска. Потребуется явно разделить серверные данные, черновики и UI-состояние | Выбран для P0 [S04–S06, S19] |
| Svelte + Svelte Flow | Рабочая альтернатива с пользовательскими узлами и связями. Другой синтаксис компонентов сам по себе не устраняет сложность сохранения, групп и нескольких представлений документа | Не выбран: преимущество для требований этого проекта пока не подтверждено пробой [S20] |
| TypeScript без UI-framework + собственный граф | Даёт полный контроль, но требует самостоятельно поддерживать компоненты, геометрию и взаимодействия редактора | Не выбран: по оценке проекта увеличивает объём собственной инфраструктуры |

Оценка простоты в таблице — инженерное решение для этого ТЗ. React отвечает за интерфейс, React Flow — за представление и взаимодействия графа, backend — за доменную валидацию и подтверждённое сохранение. Преобразования между доменными DTO и React Flow изолированы в адаптере (раздел 22.3).

Использовать обычную клиентскую SPA без обязательного SSR или второго backend. В P0 достаточно исходного Markdown и безопасного preview (раздел 8.5). Выбор библиотек редактора, общего store и доступных меню/диалогов остаётся техническим решением E0, а не основанием повторно выбирать весь frontend-стек.

### 2.2. ADR-P0-STORAGE-001 — PostgreSQL вместо SQLite

**Статус: принято владельцем 8 октября 2026 года.** Основание — прямое изменение требования: «для базы PostgreSQL». Эта запись является принятым ADR в составе ТЗ и заменяет прежнее решение D-09 редакции 1.0.

- **Воспроизводимый конфликт:** редакция 1.0 требовала SQLite в D-09 и разделе 13.2, а раздел 21.1 запрещал обязательный PostgreSQL. Выполнить эти требования одновременно с новым выбором владельца невозможно.
- **Варианты:** оставить SQLite; перейти на PostgreSQL; поддерживать обе БД. Выбран PostgreSQL. Поддержка двух БД не входит в P0: она потребовала бы двух вариантов поиска, миграций и проверки транзакций.
- **Последствия:** PostgreSQL становится обязательной службой установки; меняются драйвер, полнотекстовый поиск, блокировки, конфигурация, резервирование и интеграционные тесты. Оригиналы остаются файлами; Docker остаётся P1. Подготовка установки и E0 расширяются проверкой службы БД и её утилит; календарная оценка не задана.
- **Данные и API:** доменные UUID, JSON DTO, ревизии и переносимый архив v1 сохраняют свой смысл. SQL-схема и миграции создаются для PostgreSQL. Миграция существующей пользовательской SQLite-базы не заявляется: в проверенных checkout пока только README; при обнаружении ранее сохранённых данных требуется отдельный план переноса без их удаления.
- **Проверка:** на настоящем PostgreSQL подтвердить атомарность, конкурентные повторы и конфликты, поиск и backup/restore; AC-01, AC-35–AC-44, AC-50–AC-52, AC-65–AC-68. Эти проверки заданы, но данной редакцией документа не считаются выполненными.

**Рассинхронизация инструкций:** существующий `AGENTS.md` в разделах 2 и 5 ещё содержит SQLite. Для выбора БД применяется это принятое изменение ТЗ по приоритету раздела 0. Координатор должен синхронизировать инструкции до выдачи задач на реализацию; повторное согласование PostgreSQL не требуется. При подготовке `docs/adr/` перенести туда эту запись с сохранением ID и ссылки, не создавать конкурирующее решение.

| OQ-07 | Как синхронизировать рабочие инструкции с новой редакцией? | Обновить SQLite-требования в `AGENTS.md`, оформить ADR по разделу 2.2 в целевой структуре `docs/`, сохранить единственный нормативный файл при переносе workspace. Это подготовительная работа, не новый выбор БД | A; до выдачи задач на реализацию |

**Не являются открытыми вопросами P0:** один владелец, один граф на исследование, один уровень групп, исходный Markdown с preview, отсутствие исполнения плагинов/LLM/OSINT-коннекторов, необязательность Docker. Они уже определены в D-04–D-15 и разделе 4. Изменение этих границ требует отдельного принятого изменения ТЗ.

TraceWeave должен быть похож на него по организации рабочего пространства и основным сценариям: граф исследования, выбор сущности, просмотр атрибутов и связей, поиск и навигация. Скриншоты из `Referance/` использовать вместе с описанием функциональности Flowsint, а не как изолированный образец оформления. Автоматические enrichers, OSINT-коннекторы и вычислительные workflow входят только в отдельно определённые этапы, согласно разделам 4 и 18. [S17]

Особое внимание уделить самостоятельному развёртыванию: пользователь устанавливает сервис на своей машине или сервере, открывает браузерный интерфейс и сохраняет данные на собственном хранилище. В README Flowsint описаны Docker-based установка через `make prod` на macOS/Linux и запуск через `docker compose -f docker-compose.prod.yml up -d`, а также доступ к сервису на сервере по сети. Это ориентир для простоты установки и эксплуатации TraceWeave. [S17]

Для TraceWeave принят стек Swift/Vapor + PostgreSQL и единый внешний origin. В P0 обязательна документированная локальная установка приложения и PostgreSQL без Docker; готовая контейнерная поставка по модели Flowsint относится к P1 (D-12, раздел 21.5). Redis, Neo4j и другие дополнительные сервисы не требуются. Инструкция сетевого развёртывания должна учитывать вход, разрешённый origin, TLS и привязку портов из разделов 16 и 21.

## 5. Термины и логическая модель

| Термин | Определение |
|---|---|
| Исследование (`Investigation`) | Изолированный набор документов, отношений, материалов и отчётов |
| Узел (`Node`) | Документ с устойчивым идентификатором и смысловым типом |
| Тип узла (`NodeType`) | Название, иконка, цвет и шаблон рекомендуемых атрибутов |
| Атрибут (`Attribute`) | Именованное типизированное значение внутри документа |
| Связь (`Relation`) | Самостоятельная запись об отношении двух узлов |
| Материал (`Asset`) | Оригинальный файл и его метаданные |
| Вложение (`NodeAttachment`) | Привязка материала к документу; один материал может быть использован многократно |
| Источник (`EvidenceReference`) | Основание утверждения: другой узел, материал или внешний URL с контекстом |
| Группа | Узел типа `group` и набор его участников; не склеивание документов |
| Карточка | Расширенное визуальное представление узла непосредственно на графе |
| Инспектор | Единственная правая панель, показывающая текущий объект или множественное выделение |
| Снимок отчёта | Неизменяемая копия содержимого, из которой собран конкретный отчёт |
| Операция | Атомарное подтверждённое сервером изменение исследования |
| Рабочее состояние (`WorkspaceState`) | Масштаб, панели, выбранный элемент, открытые карточки и свёрнутые группы |

### 5.1. Инварианты

**INV-01.** Данные разных исследований не связываются прямыми FK или отношениями. Перенос создаёт копию с новыми ID.

**INV-02.** Узел существует независимо от того, виден ли он, открыт ли его документ, попал ли он в фильтр и свёрнута ли его группа.

**INV-03.** Смысловой тип узла не ограничивает его единственным видом содержимого. Все обычные типы поддерживают Markdown, атрибуты и вложения.

**INV-04.** Связи ссылаются на ID узлов, а не на заголовки, индексы массива или координаты.

**INV-05.** В P0 разрешены циклы смысловых связей. Самосвязь узла запрещена. Граф не обязан быть деревом или DAG.

**INV-06.** Группировка и сворачивание не удаляют и не перенаправляют исходные связи в базе.

**INV-07.** Кнопка `×` карточки изменяет только представление. Она никогда не удаляет документ.

**INV-08.** Бинарный оригинал после загрузки неизменяем. Редактирование или обработка создаёт новый материал с происхождением.

**INV-09.** Все подтверждённые изменения исследования выполняются в транзакции и увеличивают его ревизию ровно на единицу за пакет.

**INV-10.** Нельзя показывать «Сохранено», пока соответствующее изменение не подтверждено сервером.

**INV-11.** Импортированный/полученный обработчиком результат не считается проверенным автоматически.

**INV-12.** Снимок отчёта не меняется при последующем редактировании документов или источников.

**INV-13.** Фильтры, масштаб, открытые карточки и выделение не меняют данные исследования и не влияют неявно на состав отчёта.

**INV-14.** Архивирование, удаление в корзину, физическое уничтожение и закрытие карточки — четыре разные операции с разными названиями.

## 6. Пользовательские сценарии

### SC-01. Первое исследование

Пользователь создаёт исследование «Учебный пример». Открывается пустой граф с кратким предложением добавить первый узел. Демонстрационные данные не вставляются автоматически. Пользователь выбирает «Персона», вводит «Тестовая персона А» и дату рождения, сохраняет. Узел появляется в центре видимой области и в списке сущностей.

### SC-02. Сбор материалов

Пользователь добавляет узлы телефона и места. К персоне прикрепляет изображение, к месту — видео, к заметке — аудио. Один файл можно прикрепить к двум узлам без повторной загрузки. Удаление привязки к одному узлу не удаляет файл из другого.

### SC-03. Связи и основания

Пользователь соединяет персону с телефоном, выбирает отношение «Использует телефон», оставляет статус «Не проверено» и указывает источник. Для места создаёт отдельное отношение «Возможно связан с» со статусом «Гипотеза». Разные статусы различимы не только цветом.

### SC-04. Сравнение документов

Двойной клик по персоне открывает её карточку на графе. Двойной клик по месту открывает вторую карточку. Первая не закрывается. Одинарный клик по телефону меняет правый инспектор на телефон; обе карточки остаются открытыми. `×` карточки места закрывает только её представление.

### SC-05. Группировка

Пользователь выделяет три документа, создаёт группу «Эпизод А». Группа содержит те же документы с теми же ID. При сворачивании вместо них отображается один групповой узел; внешние связи представлены агрегированно. После разворачивания доступны исходные участники, подписи и отношения.

### SC-06. Вывод и отчёт

Пользователь создаёт узел «Вывод», записывает Markdown-текст, связывает вывод с основаниями и добавляет источники. Затем выбирает состав отчёта, проверяет предпросмотр, создаёт снимок и получает `report.md` либо ZIP с материалами. Изменение исходного вывода после экспорта не изменяет уже созданный снимок.

### SC-07. Продолжение после перезапуска

После закрытия браузера и перезапуска сервера документы, связи, группы и материалы сохраняются. На том же браузере восстанавливаются открытые карточки, масштаб и панели. На другом браузере восстанавливаются серверные данные, но допускается стандартное расположение панелей и начальный масштаб.

### SC-08. Недоступность сервера

Во время редактирования текста сервер становится недоступен. Интерфейс показывает ошибку сохранения и сохраняет локальный черновик по возможности браузерного хранилища. Структурные операции блокируются до восстановления соединения. После восстановления пользователь не теряет серверную версию из-за безусловной перезаписи старым черновиком.

### SC-09. Перенос исследования

Пользователь экспортирует исследование, запускает чистую установку приложения и импортирует архив. Создаётся новое исследование с новыми ID, но с тем же содержимым, графом, группами и проверенными оригиналами файлов. Исходная установка не требуется для просмотра результата.

## 7. Компоновка интерфейса

### 7.1. Основной экран

Компоненты рабочего пространства:

| Область | Содержимое | Размер по умолчанию |
|---|---|---|
| Верхняя панель | Название исследования, переход к списку, поиск, сохранение, отчёт, меню | Высота 56 CSS px |
| Левая вертикальная полоса | Переключатели режимов боковой панели | Ширина 48 px |
| Левая панель | Палитра, сущности, поиск, материалы, история | Ширина 280 px; изменение 240–420 px |
| Центр | Интерактивный граф и плавающая панель его инструментов | Вся оставшаяся область |
| Правая панель | Инспектор объекта либо настройки | Ширина 380 px; изменение 320–560 px |
| Нижняя строка | Состояние операций, подключение, счётчики | Высота 28 px |
| Нижняя раскрываемая панель | Человекочитаемый журнал операций и ошибок | Скрыта по умолчанию; 160–360 px |

При ширине окна меньше 1280 px панели не должны оставлять граф уже 360 px: второстепенная панель переходит в выдвижной режим. Открытие настроек справа заменяет инспектор с возможностью вернуться к последнему выбранному объекту.

Полноценный desktop-сценарий проверяется от 1024×768 CSS px. На меньших размерах панели открываются по одной поверх графа. Полная оптимизация под смартфон не входит в P0, но элементы управления не должны исчезать без возможности доступа.

### 7.2. Режимы левой панели

| Режим | Функции P0 |
|---|---|
| Добавить | Поиск по типам; добавление кликом или drag-and-drop |
| Сущности | Список документов; тип, название, количество вложений; выделение; фильтры |
| Поиск | Полнотекстовые результаты, совпавшее поле/фрагмент, переход к объекту |
| Материалы | Библиотека файлов исследования, загрузка, фильтр по формату, использование |
| История | Последние подтверждённые операции и отдельный переход в корзину |

Режимы переключаются иконками с tooltip и доступными названиями. Выбранный режим, ширина и свёрнутость сохраняются в рабочем состоянии. Переключение панели не сбрасывает граф, открытые документы или несохранённые черновики.

### 7.3. Правый инспектор

Для узла: заголовок, тип, статус, теги, основные действия; вкладки «Документ», «Атрибуты», «Материалы», «Связи», «Источники».

Для связи: её тип, направление, подпись, статус, уверенность, заметка, источники, две конечные сущности.

Для материала: исходное имя, формат, размер, SHA-256, дата загрузки, происхождение, список использующих документов и просмотр.

Для нескольких объектов: количество узлов и связей, перечень выбранного, допустимые групповые действия. Не показывать поля одного случайно выбранного объекта как общие значения.

Локальная минисхема соседей в инспекторе — P0, но только один шаг соседства. Отображать до 50 соседей и ссылку «Показать все в списке» при превышении. Это ограничение минисхемы, а не удаление остальных связей. Список должен содержать все результаты с виртуализацией/пагинацией.

### 7.4. Состояния экрана

Отдельно реализовать: загрузка; пустое исследование; пустая выдача; недоступный сервер; ошибка авторизации; частично недоступный материал; конфликт ревизий; недостаточно места; архивированное исследование.

Ошибки содержат понятное описание, допустимое действие и `requestId` для диагностики. Не показывать stack trace, SQL, пути сервера или секреты.

## 8. Поведение узлов, карточек и редактора

### 8.1. Минимальные поля документа

Любой узел поддерживает заголовок, необязательный подзаголовок, тип, Markdown-текст, произвольные атрибуты, теги, вложения, источники и пользовательскую оценку проверенности.

Узел можно создать только с заголовком. Отсутствующие необязательные сведения не заменяются фиктивными значениями. Для даты рождения неизвестный день не подставляется как 1 января.

### 8.2. Начальные типы

| Код | Русское имя | Рекомендуемые атрибуты |
|---|---|---|
| `person` | Персона | ФИО, дата рождения, псевдоним |
| `organization` | Организация | Название, регистрационный идентификатор, сайт |
| `phone` | Телефон | Исходная запись номера, нормализованная запись при возможности |
| `email` | Электронная почта | Адрес |
| `domain` | Домен | Доменное имя |
| `website` | Веб-страница | URL, дата обращения |
| `location` | Место | Координаты, адрес, описание точности |
| `event` | Событие | Дата или время, место, участники в виде связей |
| `note` | Заметка | Без обязательных дополнительных полей |
| `image` | Изображение | Автор, дата создания при наличии |
| `audio` | Аудио | Автор, длительность при наличии |
| `video` | Видео | Автор, длительность при наличии |
| `conclusion` | Вывод | Формулировка, ограничения; основания через источники и связи |
| `group` | Группа | Название логической единицы |

В P0 разрешить создание пользовательского обычного типа: название, иконка из разрешённого набора, цвет, шаблон атрибутов. Шаблоны предлагают поля, но не блокируют сохранение неполной карточки. Тип `group` системный и не может быть создан изменением пользовательского типа.

Изменение шаблона не изменяет задним числом существующие документы. Смена типа узла не удаляет атрибуты, текст или материалы. Используемый тип нельзя физически удалить; его можно скрыть из палитры.

### 8.3. Матрица взаимодействий

| Действие | Выделение | Карточки на графе | Правый инспектор |
|---|---|---|---|
| Одинарный клик по обычному узлу | Выбирает узел | Без изменений | Показывает узел |
| Двойной клик по обычному узлу | Выбирает узел | Открывает/поднимает его карточку; повторно не закрывает | Показывает узел |
| Контекстное меню → «Открыть карточку» | Выбирает узел | Открывает карточку | Показывает узел |
| Клик по другому узлу | Меняет выбор | Ранее открытые остаются | Меняет содержимое |
| `×` карточки | Не обязан менять выбор | Закрывает только эту карточку | Не закрывает инспектор |
| `×` инспектора | Без изменения данных | Без изменений | Скрывает панель |
| Клик по пустому холсту | Снимает выделение | Без изменений | Сохраняет последний объект до нового выбора или закрытия |
| Shift + клик | Добавляет/исключает из выделения | Без изменений | Показывает сводку выделения |
| Двойной клик по группе | Выбирает группу | Сворачивает/разворачивает её участников | Показывает документ группы |

**Исключение для групп:** группа не превращается в обычную большую карточку. Её документ редактируется в инспекторе/полноэкранном редакторе; двойной клик управляет составным представлением.

### 8.4. Представления обычного узла

**Компактное:** ориентир 220×80 px в мировых координатах при масштабе 1. Иконка типа, цветовой маркер, заголовок до двух строк, короткий подзаголовок, индикаторы материалов и статуса. Если места недостаточно, скрыть второстепенную информацию, а не выводить её за границы.

**Открытая карточка:** ширина 360 px по умолчанию; пользователь может изменить её в пределах 280–640 px. Высота 240–640 px; длинное содержимое имеет внутреннюю прокрутку. Заголовок, подзаголовок, часть атрибутов, Markdown/редактор, превью основного материала, переход к полному документу, `×`.

Раскрытие не создаёт второй узел, не меняет ID, не выполняет автоматическую раскладку и не перемещает соседей. Все связи остаются привязаны к тому же документу; геометрия привязки обновляется под текущий размер.

Число логически открытых карточек не ограничивать искусственным закрытием старых. Для невидимых карточек допустим lazy rendering. При очень мелком масштабе содержимое карточки может быть заменено упрощённым представлением, но состояние «открыта» сохраняется.

### 8.5. Markdown-редактор

P0: исходный Markdown, безопасный предпросмотр и переключение между ними. Поддержать заголовки, абзацы, списки, цитаты, код, таблицы, ссылки. WYSIWYG и совместное редактирование не обязательны.

Внутренние ссылки:

- `[Подпись](node:UUID)` — другой документ текущего исследования.
- `[Подпись](asset:UUID)` — материал.
- `[Подпись](relation:UUID)` — связь.

Это прикладные идентификаторы, а не команды браузеру. Рендерер перехватывает их и открывает соответствующий объект. Неизвестный ID показывает «Объект недоступен», не выполняет внешний запрос. При экспорте ссылки преобразуются в переносимый формат.

Один документ имеет **один общий frontend-draft store**. Карточка, инспектор и полноэкранный редактор читают и изменяют один черновик, а не три независимые версии текста.

Ввод текста, выделение, прокрутка, управление проигрывателем и resize внутри карточки не должны запускать перетаскивание узла. Перемещать открытую карточку можно за её заголовок.

## 9. Граф и связи

### 9.1. Навигация и выделение

P0: перемещение холста средней кнопкой или Space + drag; масштаб кнопками, колесом мыши в режиме zoom и pinch-жестом; выделение рамкой; множественное выделение; фокус на узле; «Показать всё»; «Показать выделенное»; миникарта; необязательная сетка.

Для macOS-трекпада двухпальцевая прокрутка по умолчанию перемещает холст, pinch масштабирует. Параметр «Колесо: масштаб / перемещение» доступен в настройках. Прокрутка над боковой панелью и текстом не должна двигать граф.

Диапазон масштаба — 0,1–2,5. Вокруг фокуса сохранить визуальную привязку курсора. Миникарта не перехватывает клавиатурный фокус при обычном перемещении.

### 9.2. Создание связи

Предусмотреть два равноправных способа: перетаскивание от соединительной точки к другому узлу и действие «Связать с…» с поиском конечного узла. Второй способ обязателен для клавиатуры и плотных графов.

После выбора конечного узла открывается форма: тип, направление, необязательная подпись, статус. До подтверждения линия временная и не сохраняется. Отмена не оставляет пустую связь.

### 9.3. Поля и ограничения

Связь содержит `sourceNodeId`, `targetNodeId`, `relationType`, `directed`, `label`, `noteMarkdown`, `assessment`, `confidence`, источники и служебные даты.

Начальные типы: `related_to`, `has_phone`, `located_at`, `participates_in`, `supports`, `contradicts`, `derived_from`. Допускается пользовательский текстовый тип с собственным стабильным кодом. Значение `related_to` по умолчанию ненаправленное; остальные предложенные типы по умолчанию направленные, но окончательное направление выбирает пользователь.

Разрешить несколько отношений между одной парой узлов, если различается тип или направление. Запретить точный дубликат по ключу `(исследование, концы, тип, направленность)` среди активных связей. Для ненаправленной связи порядок концов канонизировать по ID. Статус, заметка и подпись не делают дубликат отдельной связью.

Повторное создание дубликата предлагает открыть существующую запись. Связи с удалёнными узлами, с самим собой и с узлами другого исследования отклоняются сервером.

### 9.4. Отрисовка

Использовать кубические кривые Безье. Библиотечный `getBezierPath` допустим; собственный геометрический движок не требуется. [S05]

Визуальная линия — 1,5–2 px при нормальном масштабе; область попадания курсора — не менее 12 экранных px. Подпись имеет подложку и не сливается с линией. Направленная связь имеет стрелку, ненаправленная — нет.

Параллельные связи должны быть доступны по отдельности: разносятся управляемым смещением контрольных точек и/или раскрываются из списка. Не допускать ситуации, когда верхняя линия полностью скрывает остальные и их нельзя выбрать.

Статус «Гипотеза» дополнительно обозначается пунктиром/иконкой; опровержение — отдельной иконкой. Цвет не является единственным носителем смысла.

При изменении размеров и положения узлов линии обновляются в текущем кадре взаимодействия. Пользовательский изгиб связей и маршрутизация вокруг всех препятствий — P1.

### 9.5. Быстрые действия

Контекстное меню узла: открыть карточку, показать в инспекторе, связать, дублировать без связей, добавить в группу, убрать из группы, поместить в корзину.

Контекстное меню связи: открыть свойства, изменить направление, перейти к началу/концу, поместить в корзину.

Контекстное меню фона: добавить узел, показать всё, настройки графа.

Дубликат документа получает новый ID, суффикс заголовка «копия», копии текста/атрибутов и новые привязки к тем же материалам. Связи не копируются автоматически.

## 10. Группы и проекция графа

### 10.1. Членство

P0 допускает только один уровень: группа содержит обычные узлы, но не другие группы. Каждый обычный узел состоит максимум в одной группе. Группа может быть пустой после перемещения участников; она не удаляется автоматически.

Создание группы из выделения требует минимум двух обычных активных узлов. Добавление одного узла в уже существующую группу допустимо. Смешанное выделение групп и их участников при создании новой группы отклоняется с понятным объяснением.

Перенос между группами выполняется одной атомарной операцией. Не использовать геометрическое наложение как неявное изменение членства: в P0 добавление/удаление участника выполняется явной командой.

### 10.2. Координаты: одно правило для всех агентов

**В базе все координаты абсолютные, в одной мировой системе графа.** Они не зависят от масштаба, прокрутки, ширины панелей и библиотечного `parentId`.

Для обычного узла `x, y` — верхний левый угол. Для группы `x, y` — якорь её компактного представления. Развёрнутая рамка группы вычисляется из отображаемых прямоугольников всех участников с полями 24 px по сторонам и 56 px сверху для заголовка. Минимальный размер рамки — 280×180 px.

Если адаптер React Flow использует относительные координаты, перевод выполняется только в адаптере:

`childRelativeX = childWorldX - groupRenderOriginX`  
`childRelativeY = childWorldY - groupRenderOriginY`

Обратное преобразование выполняется перед отправкой команды. Нельзя сохранить относительные координаты в поле абсолютных.

При создании группы её компактный якорь равен верхнему левому углу рассчитанной рамки. Последующее перемещение отдельных участников не меняет этот якорь: после сворачивания группа возвращается к своему сохранённому компактному положению. Это предсказуемое правило, а не автоматическая раскладка.

### 10.3. Перемещение

Перемещение группы на вектор `(dx, dy)` перемещает её якорь и **каждого участника ровно один раз** на тот же вектор, включая скрытые узлы. Перенос рамки развёрнутой группы и перенос компактного узла имеют одинаковую семантику.

Если выделены группа и её участник, участник не получает двойное смещение. Сервер разворачивает выборку в множество уникальных ID перед применением операции.

### 10.4. Сворачивание

Состояние свёрнутости — часть `WorkspaceState`, а не изменение документов. При сворачивании участники перестают отображаться на основном холсте, но остаются в поиске, библиотеке сущностей и базе. Их карточки сохраняют признак «открыта» и появляются после разворачивания.

Внутренние связи полностью скрытой группы на основном холсте не отображаются. Внешние связи показываются через групповой узел, но исходные `sourceNodeId/targetNodeId` не изменяются.

### 10.5. Алгоритм видимых связей

Для каждого активного узла вычислить `visibleEndpoint(node)`:

- узел состоит в свёрнутой группе → ID этой группы;
- иначе → собственный ID узла.

Затем обработать **все активные связи**, а не только видимые до сворачивания:

1. Вычислить видимые концы.
2. Если они совпали, не показывать линию на основном холсте; сохранить исходную запись.
3. Если ни один конец не был спроецирован, показывать исходную связь.
4. Если хотя бы один конец спроецирован, объединять визуальные линии по видимым концам, типу, направленности и статусу. Для ненаправленных линий канонизировать порядок концов.
5. Для каждой агрегированной линии хранить на клиенте полный список ID исходных отношений и их число.

Агрегированная линия — **только frontend-модель**. В API записи и в PostgreSQL её быть не должно. Клик открывает список исходных связей. Удаление, редактирование или изменение статуса выполняется только после выбора конкретных исходных отношений. Нельзя удалить все отношения одним неуточнённым кликом по агрегату.

### 10.6. Разгруппировка и удаление

«Разгруппировать» удаляет членство, оставляет координаты и документы участников, а документ группы превращает в обычную заметку с сохранением его ID, текста, материалов и собственных связей.

«Поместить группу в корзину» предлагает два явных варианта:

- Только группу: участники остаются и освобождаются от членства; собственные связи группы уходят в корзину.
- Группу с участниками: группа, все участники и затрагиваемые связи уходят в корзину одной операцией.

Числа объектов показать до подтверждения. Отмена восстанавливает членство, координаты и связи исходной операции, если текущая ревизия позволяет безопасное восстановление.

## 11. Материалы и просмотр

### 11.1. Хранение и связи с документами

Материал принадлежит исследованию. Связь материала с документом — отдельная запись. У одного документа может быть много вложений, у одного материала — много использующих документов.

Вложение содержит роль `primary` или `attachment`, порядок и подпись. Основной материал у документа максимум один; его отсутствие допустимо. При смене основного материала прежний остаётся обычным вложением.

Библиотека материалов доступна независимо от графа. Загрузка в библиотеку не создаёт узел без явного выбора. Загрузка на фон графа предлагает: «Создать узлы по файлам» или «Только в библиотеку». При нескольких файлах первый вариант создаёт по одному документу на файл и показывает число создаваемых документов.

### 11.2. Форматы P0

| Категория | Принимаемые форматы | Просмотр |
|---|---|---|
| Текст | UTF-8 `.txt`, `.md` | Текст; безопасный Markdown для `.md` |
| Изображение | JPEG, PNG, WebP, GIF | Масштабирование, вписать, оригинальный размер; без изменения оригинала |
| Аудио | MP3, WAV, Ogg, M4A | Нативный плеер браузера при поддержке конкретного кодека |
| Видео | MP4, WebM, MOV | Нативный плеер при поддержке конкретного кодека |

Расширение контейнера само по себе не гарантирует воспроизведение в любом браузере. В P0 не обещать автоматическую конвертацию. При неподдерживаемом кодеке показать формат, сообщение и скачивание оригинала, а не бесконечный индикатор загрузки.

HTML, SVG, исполняемые файлы, офисные документы и произвольные архивы как обычные материалы в P0 отклоняются. Импорт ZIP исследования обрабатывается отдельным маршрутом и отдельным валидатором.

### 11.3. Лимиты по умолчанию

| Параметр | Значение |
|---|---:|
| Один оригинальный материал | 512 MiB |
| Один текстовый файл | 5 MiB |
| Одновременные загрузки клиента | 2 |
| Одновременные загрузки сервера | 4 |
| Незавершённая/неприкреплённая загрузка | Срок жизни 24 часа |
| Имя оригинального файла | До 255 Unicode scalar values |
| Размер JSON API, кроме пакетов команд и специальных импортов | 8 MiB |
| Размер JSON пакета `/commands`, включая все команды и конверт | 32 MiB |

Лимиты конфигурируемы; frontend получает их от сервера. Размеры считать в байтах: `1 MiB = 1 048 576 bytes`. Не использовать размер из заголовка клиента как единственный контроль.

По принятому CR-E2-002 тело документа ограничено 5 MiB исходного UTF-8 текста; предел пакета команд 32 MiB учитывает расширение при JSON-экранировании. Несколько крупных документов в одном пакете должны укладываться в общий предел. Capabilities сообщает `maxDocumentMarkdownBytes` и `maxCommandJsonBytes` отдельно от `maxTextBytes` (загружаемый текстовый файл) и `maxJsonBytes` (обычный JSON-запрос).

### 11.4. Процесс загрузки

1. Клиент создаёт upload-ticket: имя, предполагаемый формат, ожидаемый размер.
2. Сервер проверяет лимиты и доступ к исследованию; выделяет случайный ID, но не пользовательский путь.
3. Клиент передаёт сырые байты отдельным потоковым `PUT`.
4. Сервер потоково записывает временный файл и считает SHA-256, контролируя фактический размер.
5. После завершения проверяет размер, сигнатуру/тип и требования формата; перемещает оригинал в неизменяемое хранилище.
6. Клиент выполняет атомарную команду регистрации материала и при необходимости привязки к узлу.
7. Только после подтверждения этой команды материал считается частью библиотеки исследования.

В P0 докачка с произвольного байтового смещения не обязательна. Повтор прерванного `PUT` начинает загрузку заново и не дописывает байты в старый partial-файл. Повтор после успешно завершённой загрузки либо возвращает прежний результат для того же содержимого, либо отклоняется; нельзя молча заменить оригинал.

Upload-ticket регистрируется только один раз и связывается с конкретным `assetId`. Повтор исходного пакета обрабатывается идемпотентно; новая попытка использовать уже потреблённый ticket в другом пакете получает `409 upload_already_registered` и ID созданного материала, а не второй оригинал.

Успех одной загрузки не маскирует ошибку другой. Состояние каждого файла и возможность повтора отображаются отдельно.

### 11.5. Оригиналы и медиа

Не хранить бинарные материалы в JSON, Markdown или Base64-полях документов. Не читать весь файл в память backend-процесса для пересылки. Использовать потоковую выдачу и backpressure. Возможности файлового ввода-вывода Vapor должны быть проверены на используемой версии. [S10]

Для аудио и видео реализовать `HEAD`, одиночные HTTP Range-запросы, `206`, `416`, `Content-Range`, корректные размеры и `Accept-Ranges: bytes`. Множественный Range допускается игнорировать с возвратом полного `200`; не формировать ошибочный multipart-ответ. Перемотку проверить реальными браузерными тестами. [S11]

Ни один материал не начинает воспроизводиться автоматически. При закрытии карточки её проигрыватель останавливается. При скрытии из-за виртуализации проигрывание не должно самопроизвольно продолжаться; активный плеер либо остаётся закреплённым до остановки, либо явно останавливается.

EXIF и другая встроенная метаинформация оригинала не удаляются молча. В P0 приложение не выполняет автоматическую очистку персональных метаданных; перед передачей оригиналов в отчёте показывается предупреждение.

## 12. Модель данных и валидация

### 12.1. Общие правила сериализации

API использует JSON, UTF-8 и `camelCase`. Дублирующиеся ключи JSON, нечисловые NaN/Infinity и неизвестные поля команд отклоняются, а не трактуются по принципу «последнее значение победило». В PostgreSQL использовать `snake_case`. Публичные DTO отделены от Fluent-моделей.

Идентификаторы объектов — UUID в нижнем регистре. Клиент генерирует ID для создаваемых узлов, отношений и пакетов операций; сервер проверяет уникальность. Даты служебных событий — RFC 3339 в UTC с `Z`. Человеческая календарная дата хранится отдельно от timestamp и не сдвигается из-за часового пояса браузера.

Отсутствующее необязательное значение представлять `null`, пустую коллекцию — `[]`. В командах обновления отсутствие поля означает «не изменять», `null` — «очистить», если поле допускает очистку. Не смешивать пустую строку и неизвестное значение для типизированных атрибутов.

Ограничения длины текста, кроме отдельно указанных байтовых лимитов, считать по Unicode scalar values, не по количеству UTF-16 code units. Заголовки и ключи нормализовать NFC и обрезать пробелы по краям. Markdown не обрезать и не переписывать без явного действия пользователя.

### 12.2. `Investigation`

| Поле | Тип | Требование |
|---|---|---|
| `id` | UUID | Первичный ключ |
| `ownerId` | UUID | Владелец локальной установки |
| `title` | string | 1–200 символов |
| `descriptionMarkdown` | string | До 1 MiB UTF-8 |
| `status` | `active` / `archived` | Архивированное исследование доступно для чтения и экспорта |
| `revision` | integer | Неотрицательное, до максимального безопасного JSON integer; начальная ревизия 0 |
| `createdAt`, `updatedAt` | timestamp | Серверные даты |
| `archivedAt` | timestamp / null | Заполняется при архивировании |

Архивирование не является удалением. Редактирование архивированного исследования запрещено, кроме команды возврата в активное состояние.

### 12.3. `NodeType`

| Поле | Тип | Требование |
|---|---|---|
| `id` | UUID | Уникальный ID |
| `investigationId` | UUID | Типы изолированы по исследованию |
| `code` | string | Уникальный стабильный код внутри исследования; `[a-z][a-z0-9_.-]{0,63}` |
| `name` | string | 1–80 символов |
| `iconKey` | string | Только ключ из включённого в приложение набора иконок |
| `color` | string | `#RRGGBB`; UI проверяет читаемость производных оттенков |
| `isSystem` | boolean | Защищает системную семантику типа `group` |
| `isHidden` | boolean | Скрытие из палитры без удаления существующих узлов |
| `attributeTemplates` | array | Шаблоны: ключ, название, тип значения, необязательное начальное значение |

Начальные системные типы копируются в каждое новое исследование с новыми ID и стабильными кодами. Настройки одного исследования не меняют типы другого.

### 12.4. `Node`

| Поле | Тип | Требование |
|---|---|---|
| `id`, `investigationId`, `typeId` | UUID | Все ссылки в рамках одного исследования |
| `title` | string | 1–200 символов |
| `subtitle` | string / null | До 500 символов |
| `bodyMarkdown` | string | До 5 MiB UTF-8 (5 242 880 байт), CR-E2-002 |
| `assessment` | enum | `unreviewed`, `confirmed_by_user`, `hypothesis`, `refuted_by_user` |
| `confidence` | enum / null | `low`, `medium`, `high`; субъективная оценка пользователя |
| `tags` | string[] | До 50; каждое 1–50 символов; уникальны после нормализации |
| `createdAt`, `updatedAt` | timestamp | Не редактируются произвольно через обычный DTO |
| `deletedAt` | timestamp / null | Признак корзины |
| `deletionBatchId` | UUID / null | Связь с операцией удаления |
| `origin` | object | `kind`: `manual`, `import`, `plugin`; описание происхождения |
| `extensions` | object | Необязательные namespaced-метаданные, до 16 KiB; не исполняются |

Связанные атрибуты, вложения, источники и положение хранятся отдельно. Полный DTO документа собирает их для редактора. DTO графа отдаёт только краткое представление, а не полный текст всех документов.

`bodyMarkdown` хранится непосредственно в PostgreSQL как текст. Лимит проверяется по исходным байтам UTF-8, включая Markdown-разметку, до JSON-экранирования; сохранение не обрезает и не нормализует содержимое. Файл `.md` вместо поля БД не требуется. Предел распространяется также на документы в архиве и неизменяемых снимках; другие Markdown-поля сохраняют собственные ограничения.

`confirmed_by_user` без источника разрешён, но помечается предупреждением в инспекторе и отчёте. Приложение не должно принуждать пользователя добавлять фиктивную ссылку ради сохранения статуса.

### 12.5. `Attribute`

| Поле | Назначение |
|---|---|
| `id`, `nodeId` | Устойчивые идентификаторы |
| `key` | Пользовательское имя, 1–80 символов; кириллица разрешена |
| `normalizedKey` | Служебный NFC + Unicode case-fold + trim для уникальности внутри узла |
| `valueType` | Один из типов ниже |
| `value` | Значение строго соответствующей формы |
| `sortOrder` | Целое неотрицательное число |

| `valueType` | JSON-форма | Валидация |
|---|---|---|
| `text` | string | До 10 000 символов |
| `number` | number | Конечное число в безопасном диапазоне JSON/JavaScript; не использовать для телефонов и длинных идентификаторов |
| `boolean` | boolean | Только `true` / `false` |
| `date` | `{"value":"1987-04","precision":"month"}` | `year`, `month`, `day`; соответствие реальному календарю |
| `datetime` | string | RFC 3339 timestamp |
| `url` | string | Абсолютный HTTP/HTTPS URL, до 4 096 символов |
| `geo` | `{"latitude":61.67,"longitude":50.83,"accuracyMeters":null}` | Широта −90…90, долгота −180…180, конечные значения; точность null или положительное число |

Для даты допустимы `YYYY`, `YYYY-MM`, `YYYY-MM-DD` соответственно её `precision`. Точность координат не выводить из числа знаков после запятой автоматически.

Для отсутствующего значения атрибут можно оставить с `value: null`; это означает «неизвестно», а не пустое число или `false`. Шаблон и реальное значение валидировать одной библиотечной логикой backend; frontend повторяет ограничения для удобства, но не заменяет сервер.

### 12.6. `NodeLayout` и `GroupMembership`

`NodeLayout`: `nodeId`, `investigationId`, `x`, `y`, `zIndex`. Координаты — конечные `Double` в диапазоне ±1 000 000 мировых единиц. `zIndex` — целое в согласованном диапазоне; порядок карточек, поднятых пользователем, относится к рабочему состоянию и не обязан менять серверное `zIndex`.

`GroupMembership`: `investigationId`, `groupNodeId`, `memberNodeId`, `sortOrder`. Уникальность `memberNodeId` внутри исследования. Сервер проверяет, что контейнер — активная группа, участник — активный обычный узел и ID различаются.

Никакие поля `selected`, `dragging`, библиотечные измерения DOM или имена React-компонентов в доменные таблицы не сохраняются.

### 12.7. `Relation`

Помимо полей из раздела 9, содержит `id`, `investigationId`, служебные даты, `deletedAt`, `deletionBatchId`, `origin`. `relationType` — стабильный код 1–64 символа; русское отображаемое имя задаётся каталогом типов отношений. Подпись — до 200 символов; `noteMarkdown` — до 64 KiB UTF-8.

Концы активной связи должны быть активны. Ссылки на узлы в корзине разрешены только у связи в корзине. Уникальный индекс активных отношений должен учитывать soft delete.

Каталог `RelationType`: `id`, `investigationId`, `code`, `name`, `defaultDirected`, `isHidden`. Скрытие типа не меняет существующие связи.

### 12.8. `Asset`, `Blob`, `NodeAttachment`

`Asset` хранит `id`, `investigationId`, `blobId`, `originalName`, `title`, проверенный `mimeType`, `mediaKind`, `byteSize`, `sha256`, `createdAt`, `deletedAt`, `deletionBatchId`, `origin`, необязательные `sourceUrl`, `sourceAuthor`, `sourceCreatedAt`, `noteMarkdown`.

`Blob` — физический оригинал: ID, серверный относительный ключ хранения, SHA-256, размер, состояние доступности. Ключ хранения не возвращается обычному клиенту. Одинаковые файлы можно дедуплицировать **внутри исследования**, но это не объединяет автоматически их документальные описания. Дедупликация между исследованиями не требуется.

`NodeAttachment`: `id`, `investigationId`, `nodeId`, `assetId`, `role`, `caption`, `sortOrder`. Повтор той же пары `nodeId + assetId` не создаёт вторую привязку; обновляется подпись/порядок после явного действия.

Связи снимков отчётов с оригиналами — отдельная таблица `ReportSnapshotAsset`. Нельзя удалить blob, пока на него ссылается хотя бы один активный/удалённый материал или сохранённый снимок. Физическое удаление самой записи материала также запрещено при существующих привязках и ссылках `EvidenceReference`, пока пользователь не разрешил эти зависимости отдельными явными операциями.

### 12.9. `EvidenceReference`

| Поле | Форма |
|---|---|
| `id`, `investigationId` | UUID |
| `subjectKind`, `subjectId` | `node` / `relation` и ID утверждения |
| `sourceKind` | `node`, `asset`, `url` |
| `sourceNodeId`, `assetId`, `url` | Заполнено ровно одно поле в соответствии с `sourceKind` |
| `label` | Название источника, до 500 символов |
| `quote` | Необязательная пользовательская цитата, до 10 000 символов |
| `locator` | Необязательное описание места: страница, временной интервал, фрагмент |
| `accessedAt` | Timestamp / null |
| `note` | Пояснение, до 10 000 символов |

URL хранится как ссылка: сервер не делает HTTP-запрос ради заголовка, preview или проверки доступности. Параметры URL не вычищаются молча, но наличие возможных токенов в ссылке отмечается перед экспортом как риск.

Удаление источника в корзину не должно превращать ссылку в чужой объект с тем же заголовком. Показывать сохранённый ID и пометку о недоступности. Отчёт использует снимок источника, а не подменяет его актуальным содержимым.

### 12.10. Отчёты и системные записи

`ReportDefinition`: `id`, `investigationId`, `title`, `introductionMarkdown`, `scopeMode` (`all` / `selection`), `selectedNodeIds`, `orderedConclusionIds`, `includeGroupMembers`, `includeAttachments`, `includeEvidence`, `createdAt`, `updatedAt`.

`ReportSnapshot`: `id`, `reportDefinitionId`, `investigationId`, `sourceRevision`, `createdAt`, `formatVersion`, неизменяемый снимок выбранных документов, связей, метаданных источников и материалов. Выходной Markdown воспроизводится из этого снимка.

`OperationRecord`: `id`, `investigationId`, `revisionBefore`, `revisionAfter`, `actorId`, `clientId`, `kind`, `createdAt`, сериализованный эффект и обратимый эффект, хеш запроса, связь с отменённой/повторённой операцией. Это защищённая история внутри базы, а не обычный stdout-лог.

`UploadTicket`, `ExportJob`, `ImportJob` хранят состояния фоновых технических процессов. Изменение процента загрузки не увеличивает ревизию исследования.

### 12.11. Рабочее состояние

`WorkspaceState` хранить локально с ключом, содержащим ID пользователя и исследования. Содержимое: версия формата, масштаб/смещение, режим и размеры панелей, `expandedCardIds`, размеры карточек, `collapsedGroupIds`, последний инспектируемый объект, фильтры и настройки вида.

В localStorage допустимы только настройки представления. Содержимое документов и локальные черновики — в IndexedDB с отдельной политикой очистки. При загрузке рабочего состояния неизвестные/удалённые ID пропускаются без падения приложения.

## 13. Backend, хранилище и транзакции

### 13.1. Архитектура

Использовать модульный монолит:

`HTTP / DTO → Application Services → Domain Rules → Repository / File Storage`

Доменные правила не должны зависеть от Vapor Request, React Flow или структуры каталогов. Сервисы получают протоколы репозиториев, часы, генератор ID и хранилище файлов через явные зависимости. Не создавать сетку микросервисов для локального P0.

Рекомендуемые модули: `Investigations`, `Documents`, `Graph`, `Grouping`, `Assets`, `Evidence`, `Reports`, `ImportExport`, `Authentication`, `Operations`.

Backend использует `async/await`. Блокирующее чтение файлов, сжатие, хеширование крупных буферов и password hashing не выполняются на event-loop потоке. Для тяжёлой работы использовать ограниченный пул/очередь, а не неограниченное создание `Task.detached`.

### 13.2. PostgreSQL

Использовать Fluent + `FluentPostgresDriver` (пакет `fluent-postgres-driver`). Для полнотекстового поиска, блокировок и специальных индексов допустим SQLKit/параметризованный SQL в изолированном репозитории. Не протаскивать SQL в HTTP-обработчики. [S03]

Обязательны: отдельная БД приложения с UTF-8; версионированные миграции; foreign keys, включая составные ограничения принадлежности исследованию; уникальные и CHECK-ограничения; индексы по принадлежности исследованию, концам связей, членству, атрибутам и вложениям; GIN-индекс полнотекстового поиска. Активные отношения защищены частичным уникальным индексом с учётом soft delete. Не заменять эти ограничения только frontend-валидацией.

Использовать нативные `uuid`, `timestamptz`, `bigint` для ревизий с ограничением безопасного JSON integer, `double precision` для координат и проверяемый `jsonb` только для действительно структурированных полей. Доменные связи и целостность не заменять одним JSON-документом всего графа. Типы хранения не меняют правила публичной сериализации раздела 12.1.

P0 поддерживает один backend-процесс, одну PostgreSQL-БД и локальное файловое хранилище. PostgreSQL запускается отдельной службой, по умолчанию на той же машине. Выбор серверной БД сам по себе не добавляет несколько пользователей, несколько backend-реплик, HA или облачное хранилище.

Использовать ограниченный пул соединений и явные таймауты подключения, запроса и ожидания блокировки; значения фиксируются на E0. Доменную запись сериализовать по исследованию блокировкой его строки в PostgreSQL, а не только очередью в памяти процесса. Все пути изменения исследования, включая CLI, должны соблюдать тот же протокол. Транзакция не должна ждать загрузку файла, внешнюю сеть, кодирование видео или действия пользователя. [S07]

Многозапросные GET графа, полного документа и страницы поиска вместе с её ревизией выполняются в одной короткой `REPEATABLE READ READ ONLY` транзакции. Нельзя собирать один ответ из состояний до и после чужого commit. Экспорт и создание снимка дополнительно соблюдают закрепление оригиналов из разделов 17.4 и 17.9. [S22]

### 13.3. Транзакционный пакет

Одна пользовательская операция может создавать узел, положение, материал-привязку, несколько связей и членство. Эти изменения применяются все вместе либо не применяются совсем.

Последовательность:

1. Проверить аутентификацию и доступ к исследованию.
2. Открыть транзакцию `READ COMMITTED` и получить строку исследования через `SELECT ... FOR UPDATE` с повторной проверкой доступа. Все действия пакета выполняются на том же транзакционном соединении.
3. Проверить idempotency-key по ID пакета **до проверки устаревшей ревизии**. Для принятого пакета сравнить сохранённое тело/хеш и вернуть исходный результат либо `409 idempotency_mismatch`. Предварительный lookup вне транзакции не заменяет эту проверку после блокировки.
4. Для нового пакета сравнить `baseRevision` с текущей ревизией заблокированной строки; несовпадение даёт `409 revision_conflict` без изменений.
5. Провалидировать принадлежность всех объектов, команды и конечное согласованное состояние пакета.
6. Применить команды, обновить поисковые данные/`tsvector`, записать прямой и обратный эффект, idempotency-key, хеш и данные для повторного ответа в той же транзакции.
7. Увеличить ревизию ровно на 1 и выполнить commit. Ревизия — транзакционное поле исследования, не PostgreSQL sequence.
8. Только после успешного commit вернуть новую ревизию и ID затронутых объектов.

При ошибке любого шага пакет не должен оставлять частично созданные связи или зарегистрированные материалы. Уникальное ограничение `(investigation_id, operation_id)` дополнительно защищает журнал принятых пакетов. Два одновременных одинаковых запроса дают один эффект и один replay; разные новые пакеты с общей `baseRevision` — один commit и один конфликт. Блокировка освобождается при commit/rollback. После потери соединения с неизвестным исходом commit повторять только исходный пакет с тем же ID и телом; не объявлять его неуспешным или успешным без сверки. [S07, S22]

### 13.4. Согласование базы и файлов

Транзакция PostgreSQL и файловая система не являются общей атомарной транзакцией. Поэтому оригинал сначала безопасно завершается в staging/immutable storage, затем регистрируется в базе. Сбой между этапами может оставить осиротевший staging-файл, но не активную запись с заведомо отсутствующим оригиналом.

При старте выполнять ограниченную проверку незавершённых технических задач. Удалять только истёкшие неприкреплённые staging-объекты. Активные данные и корзину автоматически не очищать.

Наличие `refcount` допускается как ускорение, но решение о физическом удалении проверяется по всем фактическим ссылкам в транзакции. Не полагаться на счётчик, который может стать некорректным после сбоя.

### 13.5. Корзина и восстановление

Удаление обычного узла помещает его и все активные инцидентные связи в одну операцию корзины. Материалы и их оригиналы остаются в библиотеке. Привязки документа сохраняются для восстановления, но не показываются как активное использование.

Корзина показывает тип объекта, название, время и состав удаления. Восстановление по умолчанию **строгое**: весь выбранный пакет восстанавливается, только если нет конфликта ID, членства, дубликатов отношений или удалённых конечных объектов. Иначе вернуть список блокирующих условий без частичного восстановления.

Отдельная команда восстановления одного документа без его связей допустима после явного выбора пользователя. Она не должна выглядеть как полное восстановление исходного пакета.

Физическое уничтожение — только административная CLI-команда P0 с dry-run, подтверждением количества объектов и запретом удаления используемых оригиналов. Кнопка массовой окончательной очистки в UI — P1. Архивирование исследования не запускает физическую очистку.

## 14. HTTP API и команды

### 14.1. Общие требования

Базовый путь — `/api/v1`. Раздача приложения и API в production имеют один origin. Доменная запись не отдаётся напрямую из ORM без преобразования в DTO.

Перед параллельной реализацией агент контрактов создаёт полный `contracts/openapi.yaml` в OpenAPI 3.1: все запросы, ответы, ошибки, перечисления, ограничения и примеры. Из него генерируется/проверяется TypeScript API-клиент. Swift DTO проверяются contract-тестами. Создавать неполный OpenAPI с `additionalProperties: true` вместо моделей запрещено.

Контракт пишется по этому разделу, а не из уже случайно сложившихся обработчиков.

### 14.2. Ошибка

```json
{
  "error": {
    "code": "revision_conflict",
    "message": "Исследование изменено в другой вкладке.",
```

|---|---|

| 403 | Неверный Origin/CSRF или запрещённая операция |

### 14.6. Идемпотентность и конфликты

Одинаковый `operationId` и идентичное сохранённое тело запроса возвращают исходный результат с `replayed: true`; повторного изменения ревизии нет. Клиент для сетевого повтора сохраняет и повторяет исходные сериализованные байты, а не пересобирает JSON в другом порядке.

Одинаковый ID с другим телом — `409 idempotency_mismatch`. Ключи принятых доменных операций сохраняются на всё время жизни исследования, включая архив и корзину. Нельзя удалить историю ключей через час и снова принять старый пакет как новый.

Если повтор вернул старую ревизию, а клиент уже знает более новую, frontend не откатывает свой cache назад. Он подтверждает конкретную операцию и при необходимости перечитывает актуальный снимок.

Новый пакет со старым `baseRevision` — `409 revision_conflict`, без частичного применения. Сервер сообщает текущую ревизию, но не пытается угадать желаемое слияние.

### 14.7. Поиск и пагинация

Поиск ограничен текущим исследованием. Индексируются заголовки, подзаголовки, Markdown-текст, имена и отображаемые значения атрибутов, теги, подписи отношений, описания материалов и источников. Бинарные оригиналы, звук и видео не индексируются как текст без отдельного будущего обработчика.

Для P0 использовать полнотекстовый поиск PostgreSQL: `tsvector`, `tsquery` и GIN-индекс. Для индексирования и запроса явно задавать одну конфигурацию `pg_catalog.simple`, без стемминга; не полагаться на серверный `default_text_search_config`. Русская морфология, исправление опечаток и семантическая близость не обещаются. Обычный запрос преобразовывать через `plainto_tsquery` и связанные SQL-параметры: слова объединяются через AND, введённые операторы не исполняются как сырой `tsquery` или SQL. Изменённые поисковые данные обновляются в той же транзакции, что доменные записи. [S08, S23, S24]

У PostgreSQL есть ограничения размера `tsvector` и отдельной лексемы. На E0 определить стратегию индексации допустимого Markdown вместе с атрибутами; при реализации поиска E6 учесть увеличенный до 5 MiB предел документа по CR-E2-002. Разбиение поисковых данных и обработка длинных токенов должны сохранять поиск по всему документу. При разбиении слова AND-запроса могут находиться в разных фрагментах одного объекта. Нельзя молча обрезать индексируемый текст или уменьшать лимиты документов ради ограничений FTS; проверить максимальный допустимый документ и слова в его начале/конце. [S25]

Поддержать поиск по точному фрагменту телефона/домена через отдельные нормализованные поля, не полагаться для этого на разбиение FTS на токены. При использовании `LIKE` экранировать `%`, `_` и символ escape отдельно от SQL-параметризации. На E0 закрепить fixtures для кириллицы, латиницы, смешанного регистра, пунктуации, телефона и домена; смена БД не должна незаметно менять пользовательскую семантику поиска.

Результат содержит тип объекта, ID, заголовок, совпавшее поле и безопасный текстовый фрагмент. HTML из поискового индекса не вставляется в DOM. Фильтры по типу, тегу, статусу и наличию вложений комбинируются через AND; несколько значений одного фильтра — OR.

Размер страницы — 50 по умолчанию, максимум 200. Cursor включает ревизию снимка и устойчивый ключ сортировки. Если ревизия изменилась между страницами, сервер возвращает `409 cursor_stale`; клиент обновляет выдачу, а не молча пропускает или дублирует элементы.

<a id="section-15"></a>

## 15. Сохранение, локальные черновики и история

### 15.1. Автосохранение

Текст и атрибуты: debounce 750 ms после последнего изменения. Завершение редактирования и явное «Сохранить» инициируют немедленную отправку. Перемещение узлов: локальная отрисовка во время drag и один пакет после завершения жеста, а не запрос на каждый pointermove.

Команды одного клиента идут через последовательную очередь. Следующий пакет получает `baseRevision` только после результата предыдущего. Предварительно присваивать нескольким ожидающим запросам одну ревизию запрещено.

Временное optimistic-представление допустимо, но клиент хранит подтверждённый baseline. Ошибка приводит к явному состоянию несохранённости и восстановлению/повтору, а не к исчезновению изменённых данных.

### 15.2. Состояния

| Состояние | Текст интерфейса | Поведение |
|---|---|---|
| Нет изменений | Сохранено | Сервер подтвердил все изменения документа |
| Ожидает debounce/очередь | Есть изменения | Можно продолжать ввод |
| Запрос выполняется | Сохранение… | Не отправлять конфликтующий пакет параллельно |
| Ошибка сети | Не сохранено: нет соединения | Сохранить локальный черновик, предложить повтор |
| Ошибка валидации | Исправьте отмеченные поля | Не сбрасывать введённое |
| Конфликт | Требуется сверка версий | Остановить очередь и показать сравнение |
| Материал загружается | Загрузка файла… | Отдельный прогресс; не выдавать регистрацию за завершённую |

### 15.3. Черновики

IndexedDB хранит несохранённые документы с ID пользователя/исследования/узла, серверной базовой ревизией, временем и версией формата черновика. Запись выполнять с коротким debounce, ориентир 150 ms. Если квота или политика браузера запрещает запись, показать «Локальное восстановление недоступно».

Не обещать сохранение последней клавиши при аварийном завершении браузера: гарантией продукта является подтверждённая серверная запись. Локальный черновик — дополнительная защита.

При восстановлении сначала загрузить серверную версию, затем предложить восстановить/сравнить/удалить черновик. Автоматическая перезапись сервера восстановленным текстом запрещена.

При выходе из аккаунта предложить сохранить изменения, скачать Markdown-черновик или отказаться от них. После подтверждённого выхода очистить приватный cache и локальные черновики этого пользователя; настройки темы могут остаться. Токены сессии в IndexedDB/localStorage не сохранять.

### 15.4. Несколько вкладок

Совместное редактирование не входит в P0, но тихая потеря данных недопустима. Проверять ревизию при возврате фокуса и с интервалом 15 секунд, когда исследование открыто. Возможен `BroadcastChannel` для уведомлений между вкладками, но это оптимизация, не замена серверному контролю.

При конфликте: остановить очередь, сохранить пользовательский ввод, получить свежую версию, показать две версии текста/полей. Доступны «Оставить серверную», «Применить мой вариант после просмотра», «Скопировать текст». Для геометрии — показать различие и дать выбор, не переотправлять весь старый граф автоматически.

### 15.5. Undo/redo

P0: отмена/повтор подтверждённых пользовательских пакетов в текущей браузерной сессии, до 100 шагов. Серверная история операций хранится дольше, но произвольный time travel по ней не входит в P0.

Отмена действует только на верхушку текущей последовательности операций; после внешнего изменения локальный стек сбрасывается с уведомлением. Сервер проверяет, что целевая операция действительно является допустимой вершиной истории, а не доверяет frontend-массиву.

Undo/redo сами создают записи истории и новые ревизии. Повтор восстанавливает эффект без повторного выполнения внешних действий. Загрузка байтов, скачивание отчёта и выполнение будущего внешнего скрипта не «отменяются» запуском обратной программы.

Обратимы изменения документов, атрибутов, связей, положения, групп, привязок и soft delete. Создание неизменяемого снимка отчёта и административное физическое удаление — барьеры истории: UI очищает текущий undo/redo stack с понятным уведомлением. Не удалять снимок отчёта скрытой отменой.

Когда фокус внутри текстового редактора, Cmd/Ctrl+Z сначала относится к его обычной истории ввода. Кнопки истории графа работают с подтверждёнными доменными пакетами. При несохранённом черновике кнопка отмены графа предлагает сначала сохранить или отказаться от черновика.

<a id="section-16"></a>

## 16. Безопасность и приватность

### 16.1. Модель угроз

P0 защищает данные от неавторизованного обращения к серверу, вредоносного Markdown/файла, ошибочного импорта, случайной публикации наружу и непреднамеренной отправки материалов сторонним сервисам.

P0 не обеспечивает защиту от владельца ОС, администратора PostgreSQL/каталога данных, заражённого браузера или компрометации всей машины. Данные PostgreSQL и оригиналы в P0 не шифруются самим приложением; для защиты выключенного устройства требуется шифрование дисков, содержащих кластер БД, оригиналы и backup. TLS защищает соединение, но не заменяет шифрование диска. Не выдавать локальное хранение за сквозное шифрование.

### 16.2. Вход и сессии

При первой настройке создать единственного владельца административной CLI-командой. Пароль вводится интерактивно; длина от 12 Unicode scalar values, не более 1 024 байт UTF-8. Не нормализовать и не обрезать пароль молча. Не передавать его позиционным аргументом, не хранить в Git, не печатать в журнал. Публичного endpoint регистрации нет.

Использовать Argon2id через поддерживаемую готовую реализацию с проверенной сборкой macOS/Linux; конкретную зависимость и параметры зафиксировать в ADR этапа E0. Базовая конфигурация: память 64 MiB, 3 итерации, параллелизм 1; параметры хранить вместе с хешем. Самостоятельно реализовывать криптографию нельзя. При необходимости изменить параметры опираться на проверенную документацию и замеры, не переходить молча на быстрый SHA-256 пароля. [S13]

Сессия: криптографически случайный непрозрачный ID не менее 256 бит; на сервере хранится его безопасное представление и срок жизни. Cookie `HttpOnly`, `SameSite=Strict`, `Path=/`; `Secure` обязателен под HTTPS. Для явно выбранного loopback HTTP разрешается cookie без `Secure`, иначе локальный вход может не работать предсказуемо.

Срок бездействия — 12 часов, абсолютный срок — 7 дней. Login и смена пароля ротируют/отзывают сессии. После 5 неудачных попыток за 15 минут применять ограничение с `429`, не раскрывая различие «нет пользователя / неверный пароль». Проверить поведение без доверия к произвольному `X-Forwarded-For`.

### 16.3. Origin, CSRF и локальная сеть

По умолчанию слушать `127.0.0.1`, не `0.0.0.0`. Разрешённый Host/Origin задавать конфигурацией. Не использовать wildcard CORS. Для изменяющих запросов проверять Origin и CSRF-token, включая login, logout, upload и commit импорта. `SameSite` — дополнительная мера, а не единственная защита. [S12]

Доступ по LAN требует явного изменения конфигурации, а вне loopback — HTTPS через доверенный reverse proxy. Произвольным forwarded-заголовкам не доверять. Производственный frontend не должен обращаться к отдельному development-origin.

### 16.4. Markdown и ссылки

Raw HTML отключить. Исключить script, iframe, event-handler атрибуты и опасные URL-схемы. Разрешить только HTTP/HTTPS, необходимые внутренние ссылки `node:`, `asset:`, `relation:` и безопасные относительные ссылки экспортированного документа.

Внешние изображения из Markdown по умолчанию **не загружать**, чтобы открытие документа не отправляло запрос третьей стороне. Показывать ссылку и объяснение. Внешние ссылки открываются только по явному действию, с `noopener noreferrer`.

Применить CSP без `unsafe-eval`. `script-src` — свои собранные файлы; `connect-src` — свой origin; `object-src 'none'`; `frame-ancestors 'none'`; `base-uri 'none'`. Для CSS inline styles, необходимых графу, допускается узкое послабление в `style-src` с ADR. Оно не должно распространяться на inline JavaScript.

### 16.5. Файлы и архивы

Имена, Content-Type и расширения пользователя не считаются доверенными. Проверять реальный формат, размер и допустимость. Хранить оригиналы вне webroot, выдавать через авторизованный обработчик, использовать серверные ключи путей. Включить `X-Content-Type-Options: nosniff`. Для скачивания правильно кодировать `Content-Disposition`, исключая CR/LF-инъекции. [S09]

Архив не может писать в произвольный путь, создавать symlink/hardlink, менять права/владельца или исполнять файл. Проверять каждый путь после нормализации, включая Windows-разделители и drive-prefix. Не доверять `../`, абсолютным путям, повторным именам entries и заявленным размерам.

Антивирусная проверка не входит в обязательный P0, и интерфейс не должен утверждать, что файл «безопасен», только потому что прошёл проверку формата. Приложение не запускает загруженные файлы как программы.

### 16.6. Данные и внешние сервисы

Нет телеметрии, аналитических пикселей, внешних CDN, удалённых шрифтов, автоматических previews URL или внешнего crash reporting. Все runtime-ассеты входят в сборку. Проверка обновлений также не выполняется скрытно.

Логи stdout/stderr не содержат тексты документов, ФИО, телефоны, полные URL с query, cookie, пароли, строку подключения к БД или тела загружаемых материалов. Для диагностики использовать ID операций, длительности, размеры и технические коды ошибок. SQL-логи приложения и PostgreSQL не должны раскрывать значения пользовательских параметров.

Не публиковать приложение с незаполненной аутентификацией под предлогом «оно пока только локальное». Не добавлять скрытую отправку данных в LLM для подсказок и генерации отчёта.

## 17. Отчёты, экспорт и импорт

### 17.1. Узел-вывод

Узел `conclusion` — обычный полноценный документ со специальной семантикой и визуальным обозначением. Он не появляется автоматически из количества связей. Пользователь пишет формулировку, основания и ограничения.

В редакторе предложить необязательный шаблон разделов: «Вывод», «Основания», «Что не подтверждено», «Ограничения». Пустой шаблон не является реальным выводом и не заполняется вымышленными данными.

### 17.2. Состав отчёта

Пользователь задаёт название, вводный текст, режим `all` или `selection`, включение участников выбранных групп, включение материалов/источников и порядок выводов.

Состав вычислять явно:

1. `all` — все активные узлы исследования.
2. `selection` — только `selectedNodeIds` и, если выбрана опция, участники выбранных групп.
3. Добавление вывода через UI явно добавляет его в выбранный состав; backend проверяет, что `orderedConclusionIds` — подмножество итогового состава.
4. Отношения включаются, только если оба исходных конца находятся в составе. Визуальные агрегированные рёбра не экспортируются как реальные отношения.
5. Выбранные участники группы не подтягивают автоматически текст её родительского документа.
6. Источник-узел за пределами состава не подтягивается рекурсивно. В preview показать предупреждение и действие «Добавить источник в состав».
7. Для исключённого источника не копировать его документ, вложения и актуальные поля; в отчёте оставить нейтральную пометку «Источник вне выбранного состава».
8. Обычные URL и материалы, указанные в источниках включённых документов, отображаются согласно опциям источников/материалов; их фактический состав показать до экспорта.

Фильтр поиска и скрытие узлов на холсте не определяют состав отчёта. Команда «Отчёт по выделенному» один раз копирует выделение в явные `selectedNodeIds` и открывает настройки.

### 17.3. Предпросмотр

Перед созданием снимка показать: число узлов, связей, материалов, общий объём оригиналов, список выводов, непроверенные утверждения, исключённые источники, отсутствующие файлы и предупреждение о персональных данных/метаданных.

Все выбранные сущности учитываются. Нельзя сформировать отчёт только по загруженной странице левого списка или по тем узлам, которые React успел отрисовать.

Наличие недоступного файла не скрывать. Пользователь либо отменяет экспорт, либо явно выбирает текстовый отчёт с отметкой о недоступном материале. ZIP с обещанным включением всех оригиналов не должен завершаться как успешный при отсутствии одного из них.

### 17.4. Снимок

Перед снимком дождаться сохранения документов и завершения необходимых загрузок. `report.snapshotCreate` выполняется отдельно на известной `baseRevision`. Внутри транзакции копируются состав и весь текст/метаданные, требуемые для воспроизводимого отчёта. Оригиналы закрепляются ссылками на неизменяемые blobs.

`sourceRevision` равна ревизии исследования **до** создания снимка. Само создание снимка увеличивает ревизию на 1. Снимок хранит собственные `createdAt` и `formatVersion`.

Повторное скачивание того же снимка не читает изменённый текст исходных узлов. В отчёте используется время снимка, а не текущее время скачивания. Текстовое содержимое должно быть детерминированным; абсолютная байтовая идентичность ZIP между разными версиями архиватора не требуется.

### 17.5. Структура Markdown

```text
report.md
  YAML frontmatter: название, дата снимка, ID отчёта, версия формата
  # Название исследования
  ## Цель и рамки
  ## Краткие результаты
  ## Выводы
  ## Сущности и материалы
  ## Установленные и предполагаемые связи
  ## Непроверенные сведения и ограничения
  ## Источники
```

Это структура, а не команда автоматически придумывать краткие результаты. Если автор не написал резюме, раздел содержит только предоставленные им данные или не включается.

У каждого включённого узла — устойчивый anchor вида `node-UUID`. Внутренние ссылки переводятся в локальные якоря. Ссылки на невключённые документы становятся текстовыми отметками; ссылки на работающий исходный localhost в экспорт не попадают.

Источники нумеруются в порядке первого использования при фиксированном порядке секций. Дубликаты одного `EvidenceReference.id` используют один номер. Разные описания одного URL не склеиваются автоматически, потому что могут ссылаться на разные фрагменты или даты.

### 17.6. Форматы

| Формат | Содержание |
|---|---|
| `report_markdown` | Один `report.md`, без бинарных оригиналов; вместо недоступных внутри файла media-ссылок — метаданные и явное пояснение |
| `report_bundle` | `report.md`, `report.json` со снимком, `media/` с выбранными оригиналами, `manifest.json` с хешами |
| `project_archive` | Полный переносимый архив исследования, включая корзину и сохранённые снимки |

В bundle материалы именуются по UUID и проверенному расширению, например `media/40000000-0000-4000-8000-000000000001.png`. Исходное имя остаётся метаданными. Относительные пути и Markdown/YAML-строки экранируются библиотечным сериализатором.

Перед экспортом полного исследования явно указать: **архив содержит также корзину и исторические снимки, поэтому в нём могут быть ранее удалённые сведения**. Для ограниченного распространения использовать выбранный отчёт, а не полный архив.

### 17.7. Переносимый архив исследования v1

```text
research-graph-export.zip
  manifest.json
  project.json
  blobs/
    <sha256 первого оригинала>
    <sha256 второго оригинала>
```

Здесь угловые скобки обозначают правило именования entries формата, а не файлы-заглушки. Реальный экспорт содержит только реальные файлы с реальными SHA-256.

`manifest.json` содержит `format: "research-graph.archive"`, `formatVersion: "1.0"`, дату экспорта, ID исходного исследования, его ревизию, `projectPath`, `includesTrash: true`, `includesSnapshots: true` и полный список файлов с путём, размером и SHA-256. Список включает `project.json` и все blobs; сам manifest не включает рекурсивный хеш самого себя.

`project.json` содержит метаданные исследования без учётной записи, каталоги типов, все активные и удалённые документы, атрибуты, положения, членство, связи, материалы, привязки, источники, определения отчётов, снимки, ссылки снимков на материалы и метаданные пакетов корзины.

Для переносимого восстановления корзины использовать `DeletionBatch`: ID, время, список затронутых объектов и сохранённое прежнее членство. Не требовать наличия всей серверной `OperationRecord` для возврата импортированных документов из корзины.

Пароли, сессии, CSRF-token, пути ОС, незавершённые загрузки, локальные черновики и журнал idempotency-key в проектный архив не включаются. Экспорт исследования — не полная резервная копия установки.

### 17.8. Импорт

Только в новое исследование, без слияния с существующим и без перезаписи по совпавшему UUID. Процесс: upload → безопасная распаковка в staging → проверка формата → проверка всех хешей и ссылок → план → подтверждение → атомарное создание.

| Лимит архива по умолчанию | Значение |
|---|---:|
| Сжатый архив | 10 GiB |
| Суммарный фактически распакованный объём | 20 GiB |
| Количество entries | 50 000 |
| `project.json` | 64 MiB |
| Один blob | Лимит соответствующего обычного материала, не более 512 MiB |
| Максимальное отношение распакованного размера к сжатому | 1 000:1; дополнительно действуют абсолютные лимиты |

Если полный экспорт превышает стандартные лимиты будущего импорта, показать предупреждение и требуемые настройки принимающей установки. Не урезать архив молча; разбиение на тома в P0 не требуется.

Счётчики контролируются в потоке, а не только по ZIP-заголовкам. До commit данные остаются невидимыми как исследование. Сбой не оставляет половину графа.

Создать таблицу замены **всех** внутренних UUID, включая удалённые объекты и объекты внутри снимков. Переписать ссылки в DTO и распознанные внутренние Markdown-ссылки; не выполнять произвольный строковый replace UUID во всём тексте. Стабильные коды типов не менять.

Исторические документы внутри снимков остаются замороженными копиями; их наличие не должно создавать лишние активные узлы. Старую ревизию снимка обозначать как ревизию исходного исследования, сохранив происхождение импорта. Новое исследование имеет собственную последовательность ревизий.

Неподдерживаемая major-версия архива отклоняется. Неизвестные обязательные поля/типы не игнорируются молча. Совместимые minor-расширения обрабатываются по явно описанной миграции формата.

### 17.9. Задания экспорта/импорта

Состояния: `queued`, `running`, `succeeded`, `failed`, `cancelled`. Только `succeeded` предоставляет download/commit. Ошибка хранит безопасный код и пояснение, но не полный stack trace.

Экспорт полного исследования сначала фиксирует согласованный снимок на запрошенной ревизии, затем собирает ZIP вне write-транзакции. Нельзя прочитать часть таблиц до изменения, а часть после и назвать это единым экспортом.

Готовые технические export-файлы можно удалить через 24 часа: пользователь может повторно собрать файл из сохранённого снимка. Истечение download-файла не удаляет сам отчёт и его закреплённые материалы.

## 18. Расширяемость и протокол плагинов v1

### 18.1. Что сделать сейчас

P0 включает формальное описание, JSON Schema Draft 2020-12, согласованные примеры и тест их валидации. Файлы схем в комплекте являются исходной формой контракта. В приложении не должно быть действующего HTTP endpoint для запуска произвольной shell-команды.

Плагин — внешний обработчик: получает описание входов и локальные копии выбранных материалов, записывает файлы результатов и JSON-манифест. Язык реализации не важен. Обработчик не получает прямого доступа к PostgreSQL, учётным данным БД, storage-каталогу приложения или пользовательской сессии.

### 18.2. Почему файловый контракт

Он позволяет передавать текст и большие медиа без Base64, не привязан к конкретному языку и может использоваться как ручным внешним процессом, так и будущим изолированным worker.

«Передать ссылку на изображение» в базовом протоколе означает передать **относительный путь к предоставленной копии файла**, а не внутренний URL с сессионным cookie. Поддержку ограниченных одноразовых HTTP-ссылок можно добавить позднее отдельной версией протокола.

### 18.3. Структура одного задания

```text
job-directory/
  manifest.json
  request.json
  input/
    source.txt
  output/
    result.json
    result-note.txt
```

Имена входов/артефактов не фиксированы, но пути должны оставаться в своих каталогах. Для протокола v1 использовать относительные ASCII-пути; исходное пользовательское имя не превращать в путь файловой системы. `manifest.json` описывает плагин; `request.json` — конкретное задание; `output/result.json` — итог выполнения. Примеры этих файлов включены в поставку ТЗ.

### 18.4. Manifest

Содержит:

| Поле | Назначение |
|---|---|
| `format`, `protocolVersion` | Формат и версия протокола |
| `plugin.id`, `plugin.version`, `plugin.name` | Стабильная идентичность, semver и отображаемое имя |
| `description` | Краткое назначение |
| `acceptedInputKinds` | `text`, `image`, `audio`, `video` |
| `producedArtifactKinds` | Возможные категории выходных материалов |
| `suggestedNodeTypes` | Ожидаемые смысловые типы результатов, кроме группы |
| `permissions` | Запрошенные сетевые возможности; это не автоматическое разрешение |
| `limits` | Заявленные ограничители времени, памяти и размеров |
| `parameterSchema` | Схема объекта параметров; загрузка её внешних `$ref` запрещена |

В v1 manifest **не содержит исполняемую shell-строку**. Способ запуска в будущем определяет доверенная конфигурация хоста. Недоверенный файл описания не может назначить себе произвольную команду на сервере.

### 18.5. Request

Request содержит `jobId`, дату, точную пару ID/версии плагина, ограниченный контекст исследования, выбранные узлы и материалы, массив явно переданных входов, параметры, `allowedNodeTypes`, `allowedRelationTypes` и лимиты хоста.

У каждого входа: локальный ID, категория, относительный путь `input/...`, MIME, фактический размер, SHA-256; необязательные ID исходного документа и материала. Передаются только выбранные пользователем данные. Привязка к одному узлу не даёт доступ к его соседям или всему исследованию.

Лимиты хоста имеют приоритет над заявленными лимитами плагина. Схема параметров проверяется до запуска в будущей реализации; JSON Schema сама по себе не предоставляет сетевой доступ.

### 18.6. Result

Result содержит:

- ID задания и идентичность плагина, совпадающие с request.
- Статус `succeeded` или `failed`, предупреждения и безопасное описание ошибки.
- Полный список артефактов: локальный ID, категория, путь `output/...`, MIME, размер, SHA-256, заголовок.
- Предложения новых узлов: локальный ID, смысловой тип, заголовок, Markdown и ID используемых артефактов.
- Предложения отношений между новыми узлами и/или явно переданными исходными узлами.

Плагин не назначает постоянные UUID новым объектам и не передаёт статус «подтверждено». Он не имеет операций update/delete существующего графа. Новые документы и отношения после будущего импорта по умолчанию получают `unreviewed` и происхождение `plugin`.

При `failed` массивы предложений и артефактов пусты, `error` обязателен. Частичный успех в v1 не поддерживается: его нужно выразить как `succeeded` с явными предупреждениями и только корректными результатами.

### 18.7. Валидация сверх JSON Schema

Схема проверяет структуру, но этого недостаточно. Хост дополнительно проверяет:

1. Совпадение задания и плагина; поддержку версии.
2. Уникальность локальных ID и наличие всех ссылок на артефакты.
3. Принадлежность исходных node ID разрешённому списку request.
4. Отсутствие самосвязей, недопустимых типов и точных дубликатов предложенных отношений.
5. Безопасную нормализацию путей; запрет абсолютных путей, `..`, обратных слешей, symlink и выхода через родительский каталог.
6. Соответствие фактических размеров, SHA-256 и MIME; сумму **всех** выходных артефактов.
7. Соблюдение лимитов по времени/ресурсам в будущем runner; самодекларация плагина их не обеспечивает.
8. Безопасный Markdown и отсутствие автоматического открытия выходных HTML/исполняемых файлов.

Контрольная сумма подтверждает совпадение байтов с декларацией, но не доказывает истинность результата или доверенность автора.

### 18.8. Будущий процесс применения, P1

Сначала импортировать результат в staging и показать preview создаваемых узлов, отношений и материалов. Пользователь выбирает, что принять. Зависимые предложения без принятого артефакта/узла не применяются. Затем одним пакетом зарегистрировать выбранные материалы и создать документы/связи. Первый принятый `artifactId` документа по порядку становится его основным вложением; остальные — обычными, с возможностью изменить выбор в preview.

Зафиксировать происхождение: plugin ID/version, job ID, время, контрольные суммы входов, параметры без секретов и ID исходных документов. Это позволяет проследить происхождение, но не гарантирует повторяемость недетерминированного внешнего обработчика.

### 18.9. Будущий запуск, P2

Недоверенный код не исполнять внутри процесса Vapor. Worker имеет отдельного пользователя, read-only входы, отдельный writable output, лимиты CPU/RAM/времени/числа процессов, отсутствие доступа к основному каталогу данных и сети по умолчанию.

Не монтировать Docker socket в веб-приложение ради «безопасного запуска». Не считать контейнер сам по себе доказательством достаточной изоляции. Конкретная модель sandbox, разрешений и отмены задания требует отдельного ADR и security-тестов.

## 19. Визуальная система, темы и доступность

### 19.1. Темы

Три настройки: «Системная», «Светлая», «Тёмная». Системная следует `prefers-color-scheme`. Переключение не перезагружает исследование и не сбрасывает черновики.

Использовать CSS custom properties для фона, поверхностей, границ, основного/вторичного текста, акцента, ошибок, выбранного объекта и статусов. Разбросанные по компонентам hex-значения, которые не реагируют на тему, запрещены.

Пример исходной палитры собственного интерфейса, которую нужно проверить контрастом в реализации:

| Токен | Светлая | Тёмная |
|---|---|---|
| `--bg-canvas` | `#F3F5F7` | `#15191F` |
| `--bg-panel` | `#FFFFFF` | `#1D232C` |
| `--bg-elevated` | `#FFFFFF` | `#252D39` |
| `--text-primary` | `#19212B` | `#EDF1F7` |
| `--text-secondary` | `#4B586B` | `#B2BED0` |
| `--border` | `#B7C0CD` | `#65738A` |
| `--accent` | `#2457C5` | `#8FB5FF` |
| `--danger` | `#AC2434` | `#FF9BA8` |

Тип узла имеет свой семантический цвет, но текст не обязан рисоваться этим цветом. Цвет применяется к маркеру/рамке/приглушённой подложке; читаемость текста обеспечивается токеном темы.

### 19.2. Типографика и переполнение

Базовый текст интерфейса — 14 px, текст длинного документа — 16 px, вспомогательные подписи — не меньше 12 px вне масштабируемого графа. Межстрочный интервал документа — ориентир 1,5.

Адаптация размера означает ограниченный `clamp`, смену плотности и скрытие второстепенных элементов. **Не уменьшать произвольно шрифт до нечитабельного размера ради длинного заголовка.**

Для заголовков карточек: line-clamp и tooltip/полное название в инспекторе. Для URL, хешей и длинных слов: `overflow-wrap: anywhere`. Для таблиц и блоков кода: собственная горизонтальная прокрутка внутри документа, а не выход за панель. Flex/grid children должны корректно иметь `min-width: 0`.

Масштабирование самого графа может уменьшать узлы целиком. На малом масштабе применять уровни детализации: показывать иконку/короткую подпись вместо полного документа. Переключение детализации не закрывает карточки и не изменяет содержимое.

### 19.3. Иерархия и компоненты

Скругление панелей/карточек — 8–12 px, отступы по сетке 4/8 px. Тени умеренные, только для плавающих слоёв. Анимации необязательны и отключаются при `prefers-reduced-motion`.

Иконки выбираются из локально включённого открытого набора с проверенной лицензией. Иконка без текста должна иметь tooltip и accessible name. Кнопки удаления визуально отделять от закрытия карточки.

### 19.4. Клавиатура

| Комбинация | Действие |
|---|---|
| Cmd/Ctrl+K | Поиск/палитра действий приложения |
| Cmd/Ctrl+S | Немедленно сохранить текущие изменения; не открывать системное сохранение HTML |
| Cmd/Ctrl+Z | Undo редактора при фокусе в нём, иначе история графа |
| Cmd/Ctrl+Shift+Z | Redo в соответствующем контексте |
| Enter | Открыть карточку единственного выбранного обычного узла |
| Delete/Backspace | Предложить удаление выбранного, только когда фокус не в поле ввода |
| Space + drag | Перемещение холста |
| Shift + клик | Множественный выбор |
| Escape | Закрыть ближайшее меню/диалог или отменить временное соединение; не закрывать все карточки |

Не перехватывать системные комбинации глобально при вводе в поле. Поддержать Tab-навигацию, видимый фокус, focus trap в модальных диалогах и возврат фокуса к вызвавшему элементу.

### 19.5. Проверяемая доступность

Цель для панелей/форм — применимые требования WCAG 2.2 AA: достаточный контраст, управление клавиатурой, программные названия полей, понятные ошибки, отсутствие зависимости только от цвета. Это цель проверки, а не декларация сертификации. [S15]

Точечные drag-handles могут быть мелкими визуально, но должны иметь увеличенную область нажатия и альтернативное действие через меню/форму. Для двумерного графа предусмотреть эквивалентный список сущностей и отношений.

Проверить увеличение текста/масштаба браузера до 200%: формы и меню остаются доступны, критические кнопки не выходят за окно. Для сложного двумерного холста допускается панорамирование, но не потеря доступа к инспектору и командам.

## 20. Производительность и нефункциональные требования

### 20.1. Измеряемая конфигурация

Референсная машина для измерений: MacBook с Apple M1/M2, не менее 16 GiB RAM, локальный SSD; PostgreSQL и backend работают на этой же машине. В отчёте указывать точную модель, ОС, браузер, версию сборки, версию/настройки PostgreSQL, параметры пула соединений и настройки энергосбережения. Удалённая БД измеряется отдельно и не подменяет локальный эталон. Дополнительно проверить release-сборку backend на Linux x86_64 и доступной CI-конфигурации Linux arm64; отсутствие одной из платформ фиксировать как непроверенное, а не как успешно поддержанное.

Браузеры P0: актуальные стабильные Safari/macOS, Chrome, Firefox; Edge проверяется как дополнительный Chromium smoke-test. Номера фактически протестированных версий зафиксировать. Headless WebKit-тест не заменяет ручной smoke-test настоящего Safari.

### 20.2. Нагрузочные наборы

| Набор | Состав | Назначение |
|---|---|---|
| Small | 50 обычных узлов, 100 связей, 5 групп, 20 материалов | Базовая функциональность |
| Target | 900 обычных узлов + 100 групп, 3 000 связей, 200 материалов; 20 одновременно открытых карточек | Обязательная нагрузка P0 |
| Stress | 4 500 обычных узлов + 500 групп, 15 000 связей, 1 000 материалов | Диагностика деградации; без обещания полного FPS P0 |

Генератор должен строить весь набор и не выдавать за 1 000 узлов граф из 200 DOM-элементов без скрытой модели остальных. Виртуализация допустима, но количество данных и доступных объектов должно быть проверяемым.

### 20.3. Цели для Target

| Показатель | Порог P0 |
|---|---|
| Первичная готовность графа после успешного входа на локальном сервере | Не более 3 секунд, без декодирования всех media-оригиналов |
| Выбор уже загруженного узла и обновление краткого инспектора | p95 не более 150 ms |
| Серверный поиск по прогретому индексу | p95 не более 300 ms |
| Полная выдача поиска с debounce 250 ms | p95 не более 700 ms |
| Простая транзакционная правка без загрузки бинарных файлов | p95 не более 250 ms на локальном сервере |
| Панорамирование/перенос в release frontend | В 30-секундном тесте не менее 95% межкадровых интервалов ≤33,4 ms; отсутствие зависания >200 ms |
| Перемотка поддерживаемого локального видео | Начало воспроизведения выбранного места не более 2 секунд на тестовом файле |

Для p95 собрать не менее 100 измерений после прогрева и взять элемент с индексом `ceil(0.95 × N)` в отсортированной полной выборке, считая индексацию от 1. Нельзя отбрасывать медленные успешные операции без заранее описанного правила.

Тест загрузки 512 MiB не должен увеличивать RSS backend примерно на размер всего файла. Ориентир дополнительной памяти одной загрузки — ≤64 MiB; отклонение требует замера и исправления буферизации, а не увеличения лимита «на всякий случай».

### 20.4. Подходы

Краткие DTO для графа; lazy loading полных документов; мемоизированные node/edge-компоненты; обновление только затронутых элементов; виртуализированные списки; отложенная загрузка media; отсутствие тяжёлого пересчёта всего графа на каждый ввод символа. Возможности и ограничения React Flow по производительности учитывать, но целевые показатели подтверждать собственными измерениями. [S16]

Не хранить весь граф одним гигантским реактивным объектом, изменение которого перерисовывает каждый документ. Не запускать force-layout непрерывно: P0 — ручное размещение.

При Stress допустимо предложить сворачивание групп, ограничение видимых подписей и режим фокуса на соседях. Нельзя молча отрезать узлы/отношения или подменять полную выдачу первыми 1 000 элементами.

## 21. Запуск, данные, резервирование и Docker-ready

### 21.1. Локальная эксплуатация P0

Backend должен запускаться на macOS и Linux с обязательной локальной службой PostgreSQL. Redis, Neo4j, облачный аккаунт, внешний API-ключ и Docker для P0 не требуются. Node.js требуется для сборки/разработки frontend, но не как второй обязательный production-сервер: собранные Vite ассеты отдаёт Vapor.

Инструкция установки должна описывать установку зафиксированной версии PostgreSQL, запуск службы, создание отдельной базы и роли приложения без superuser, применение миграций и создание владельца TraceWeave. Вход пользователя в приложение и роль подключения к PostgreSQL — разные учётные записи. По умолчанию PostgreSQL доступен только локально; браузер обращается к Vapor и никогда не получает реквизиты БД.

Относительные каталоги по умолчанию:

```text
var/
  data/
    blobs/
    staging/
    exports/
  backups/
```

Рабочий каталог файлов находится вне исходного кода и `Public/`; пути можно переопределить конфигурацией. Кластер PostgreSQL размещается отдельно и управляется службой БД; `RG_DATA_DIR` не является каталогом PostgreSQL. Не хранить runtime-данные, SQL-дампы или реквизиты подключения в Git и не смешивать их с `Referance/`. Копия только `RG_DATA_DIR` не является полной резервной копией установки.

### 21.2. Конфигурация

| Переменная | Назначение | Значение по умолчанию |
|---|---|---|
| `RG_BIND_HOST` | Адрес прослушивания | `127.0.0.1` |
| `RG_PORT` | HTTP-порт | `8080` |
| `RG_PUBLIC_ORIGIN` | Разрешённый внешний origin | `http://127.0.0.1:8080` |
| `RG_DATABASE_URL` | Строка подключения к выделенной PostgreSQL-БД; содержит секреты | Обязательна, безопасного общего значения нет |
| `RG_DATABASE_TLS_MODE` | Режим TLS соединения с PostgreSQL: `verify-full` или `disable` | `verify-full`; `disable` разрешён только при явно настроенном loopback-подключении |
| `RG_DATABASE_CA_FILE` | Файл доверенного CA для PostgreSQL, если он не входит в системное хранилище | Не задан; используются системные доверенные CA |
| `RG_DATA_DIR` | Каталог оригиналов, staging и готовых экспортов | `var/data` |
| `RG_BACKUP_DIR` | Каталог резервных копий | `var/backups` |
| `RG_MAX_ASSET_BYTES` | Максимум оригинала | `536870912` |
| `RG_MAX_ARCHIVE_BYTES` | Максимум входного ZIP | `10737418240` |
| `RG_LOG_LEVEL` | Уровень технических логов | `info` |
| `RG_TRUSTED_PROXY_CIDRS` | Разрешённые reverse proxies | Пустой список |

Конфигурация проверяется при старте. Невозможный путь, недоступная запись, конфликт origin/режима HTTPS, отсутствие БД, неверные реквизиты, неподдерживаемая версия PostgreSQL или схемы приводят к ясной ошибке запуска без раскрытия секретов. Не создавать новую пустую базу и не переключаться на другое хранилище при ошибке подключения. База создаётся только явным шагом установки.

Для подключения к БД вне loopback обязательны TLS, проверка цепочки сертификата и имени сервера; режим `verify-full` должен обеспечивать обе проверки. Не разрешать незаметный fallback на соединение без TLS. Реквизиты доступны только backend/административным утилитам через защищённую конфигурацию, не через frontend bundle или отслеживаемый Git-файл. При потере БД во время работы readiness становится неуспешным, новые записи возвращают `503`, а UI сохраняет неподтверждённый черновик.

### 21.3. Команды для разработчика

Рабочее пространство должно предоставлять рабочие команды из корня проекта; они обращаются к отдельным checkout в `SRC/TraceWeaveBackend/` и `SRC/TraceWeaveFrontend/`:

| Команда | Реальное действие |
|---|---|
| `make setup` | Проверка toolchain, PostgreSQL и утилит backup/restore; установка зафиксированных зависимостей, без изменения пользовательской БД |
| `make dev` | Проверка доступности настроенной PostgreSQL-БД, запуск backend и Vite development server с корректным API proxy |
| `make build` | Release-сборка backend и frontend |
| `make test` | Unit/integration/contract-тесты; интеграционные проверки на изолированной PostgreSQL-БД |
| `make e2e` | Браузерные сценарии с реальным backend на тестовой PostgreSQL-БД |
| `make verify` | Форматирование/lint, typecheck, схемы, тесты и сборка |
| `make seed-demo` | Явное создание полностью синтетического учебного исследования |

Команды не должны быть заглушками, печатающими текст. `setup` не создаёт предсказуемый пароль. `seed-demo` не запускается автоматически в production.

### 21.4. Резервные копии

Для P0 реализовать **offline-backup приложения**: backend, фоновые задания и изменяющие CLI остановлены, PostgreSQL продолжает работать для `pg_dump`. На всё время операции удерживать эксклюзивную session-level advisory maintenance-блокировку на выделенном соединении PostgreSQL. Backend, мигратор и изменяющие CLI должны брать shared-блокировку того же ресурса на время своей работы; при занятой блокировке backup отклоняется до копирования. Потеря соединения, удерживающего блокировку, прерывает соответствующую работу; продолжение требует повторного получения блокировки. Прямые сторонние изменения таблиц/оригиналов во время backup запрещены.

Состав backup: дамп выделенной БД через `pg_dump` в custom-format, все оригиналы из `blobs/`, manifest с версиями приложения/схемы/PostgreSQL/утилит и контрольными суммами дампа и каждого оригинала. Дамп БД согласован сам по себе; общую согласованность с файлами обеспечивает запрет записей и удаления оригиналов на всё время копирования. Неполный backup не помечается успешным. Staging и пересоздаваемые export-файлы не являются сохранёнными пользовательскими данными; незавершённые jobs после восстановления переводятся в явное прерванное состояние. [S07, S14]

Восстановление выполняется при остановленном приложении в **новую пустую PostgreSQL-БД и чистый каталог файлов** через `pg_restore`. До запуска проверить совместимость версий, миграции, все хеши и ссылки на оригиналы; затем отозвать прежние сессии. Не перезаписывать существующую установку по умолчанию. Runbook должен описывать создание роли и прав при переносе: дамп одной БД не заменяет настройку ролей кластера. Версии `pg_dump`/`pg_restore` фиксируются и проверяются вместе с сервером на E0. [S14]

Копирование одного каталога файлов приложения либо файлов работающего PostgreSQL-кластера не считается реализацией этого backup. Online-backup приложения — P1: кроме согласованного дампа потребуется закрепление всех необходимых blobs до окончания операции.

Резервная копия всей установки может содержать учётную запись, историю и другие приватные данные; хранить её как секретный архив. Проектный экспорт, напротив, исключает сессии и пароли. В инструкции восстановления потребовать отзыв прежних сессий после переноса/восстановления установки.

### 21.5. Подготовка к Docker

P0: environment-based configuration, внешний writable каталог файлов, отдельное подключение к PostgreSQL, отсутствие зависимости от путей конкретного пользователя, корректный SIGTERM, health endpoints, воспроизводимая Linux-сборка, отсутствие state внутри frontend-build.

P1: multi-stage Dockerfile с зафиксированными версиями; непривилегированный пользователь приложения; отдельные volumes для файлов и PostgreSQL; writable staging внутри выделенного каталога; `127.0.0.1:8080:8080` как безопасная привязка HTTP-порта хоста; healthcheck; корректный graceful shutdown. Compose включает приложение и PostgreSQL, порт БД по умолчанию не публикуется на хост; защищённый способ подключения приложения к БД описывается явно.

Контейнерная поставка P1 должна обеспечивать простой самостоятельный запуск по образцу Flowsint (раздел 3.3): документированная настройка environment, запуск через Docker Compose, доступ к браузерному интерфейсу и сохранение данных в volume после перезапуска. Конкретные команды и конфигурация относятся к TraceWeave; состав сервисов Flowsint не переносится автоматически. [S17]

Внутри контейнера процесс слушает `0.0.0.0`, но публикация порта по умолчанию ограничена loopback хоста. Не путать эти два разных уровня привязки.

Несколько backend-реплик не входят в P0/P1 только на основании выбора PostgreSQL: для них нужны отдельные решения о файловом хранилище и фоновых заданиях. Контейнеризация не должна незаметно менять backend на Rust или добавлять обязательную распределённую инфраструктуру сверх принятой PostgreSQL-БД.

### 22.4. Уточнения геометрии и поиска

При переносе множественного выделения, содержащего группы и отдельные узлы, клиент исключает из `layout.move` участников уже перемещаемых групп. Сервер дополнительно проверяет пересечение затрагиваемых ID у movement-команд пакета и отклоняет неоднозначное двойное перемещение.

Обычный поиск меняет список и подсветку, не скрывая остальной граф. Опциональный P0-режим «Только результаты» — явно включаемый фильтр представления: при построении агрегатов учитываются только исходные связи, оба конца которых допущены текущим фильтром. При этом алгоритм всё равно обходит полный серверный набор данных, а не только отрисованные элементы.

Переход к найденному узлу внутри свёрнутой группы раскрывает эту группу локально. Если режим отображения скрывает узел, UI предлагает показать его и явно меняет соответствующий фильтр; не перемещать камеру в визуально пустое место.

## 23. Стратегия тестирования

### 23.1. Unit-тесты

Валидация всех значений атрибутов; нормализация ключей/тегов; допустимые типы узлов; канонизация ненаправленных отношений; запрет дубликатов/самосвязей; перемещение группы; вычисление проекции; формирование состава отчёта; переписывание внутренних ссылок при импорте; проверка безопасных путей и лимитов.

Для проекции групп добавить property-based или генеративные тесты: на случайных графах сворачивание/разворачивание не меняет множество исходных отношений; сумма исходных ID во всех агрегатах и отдельных видимых связях точно соответствует проецируемому набору, без потерь и повторов.

### 23.2. Интеграционные тесты

Настоящая изолированная PostgreSQL-БД той же поддерживаемой major-версии, с теми же миграциями, ограничениями и поисковой конфигурацией, что production; временный storage-каталог. Проверяются транзакции и rollback, FTS/GIN, soft delete/restore, конкурентная идемпотентность через разные соединения, конфликт ревизий, FK между исследованиями, согласованность многозапросных чтений, загрузка и Range, отсутствующий файл, заполненный диск/ошибки записи, недоступность БД и восстановление после сбоя на границе файловой системы и DB. Подмена PostgreSQL другой БД или in-memory store не считается интеграционной проверкой.

Тесты используют отдельные реквизиты `RG_TEST_DATABASE_URL`, отдельную временную БД на прогон и отдельный каталог. Роль тестов не должна иметь прав на пользовательскую БД; команды проверяют тестовое назначение подключения до миграций/seed/очистки. Не использовать production `RG_DATABASE_URL` или пользовательский `RG_DATA_DIR` как fallback. PostgreSQL для тестов может быть локальной службой или сервисом CI; Docker не становится обязательным условием локальной проверки.

### 23.3. Frontend и E2E

Компонентные тесты проверяют самостоятельные состояния форм, ошибки, длинный текст, общие черновики, контекстные меню и keyboard handling.

E2E выполняются против реального backend. Browser storage может содержать рабочие настройки, но не заменять отсутствующую серверную реализацию. Удаление localStorage после сохранения не должно уничтожить исследование.

### 23.4. Безопасность

Отдельные негативные наборы: XSS в Markdown/атрибутах/заголовках файлов; `javascript:` URL; внешнее изображение; неверный Origin/CSRF; доступ к чужому ID; поддельный MIME; CRLF в имени; oversized upload; path traversal; symlink; ZIP bomb; повторные entries; неверный SHA; неподдерживаемая версия архива; изменённый job ID плагина; ссылка результата на неразрешённый исходный узел.

Изображения с огромными декларируемыми размерами не декодируются автоматически для превью. Ввести `maxImagePreviewPixels`, по умолчанию 32 миллиона пикселей: более крупный разрешённый оригинал хранится, но показывается как метаданные/скачивание до отдельного явного действия. Проверка заголовков формата должна быть ограничена по ресурсам; P0 не требует создания серверных миниатюр.

### 23.5. Визуальные тесты

Снимки собственных экранов в светлой/тёмной темах на 1440×900 и 1024×768; длинные кириллические заголовки, emoji, непрерывный URL/хеш, множество атрибутов, открытые меню у края окна, несколько карточек и раскрытые панели.

Пиксельное совпадение со Flowsint не является критерием. Критерии: требуемая компоновка, отсутствие переполнений, различимость выбранного, доступность действий и сохранение рабочего пространства.

### 23.6. Доказательства прохождения

Для каждого AC в отчёте указать: автоматический test ID или ручной протокол, версию сборки, окружение, результат, ссылку на лог/скриншот при необходимости. Статусы: `passed`, `failed`, `not_run`, `blocked`. `not_run` не считается успехом.

Минимальный процент line coverage не заменяет эти проверки. Нельзя отключать неудобный тест или менять ожидания только потому, что реализация ведёт себя иначе.

## 25. Работа нескольких ИИ-агентов

### 25.1. Роли

| Агент | Ответственность | Основные зоны владения |
|---|---|---|
| A — координатор/контракты | Решения, OpenAPI, общие типы, миграционный реестр, интеграция | `contracts/`, `docs/adr/`, общие DTO, composition root, корневые lock/build-файлы |
| B — backend core | Исследования, документы, связи, группы, операции | Назначенные core-модули backend и их тесты |
| C — файлы/отчёты | Storage, uploads, media, export/import, snapshots, backup | Назначенные asset/report-модули backend и их тесты |
| D — frontend graph | Холст, адаптер, карточки, геометрия, взаимодействия, группы | `SRC/TraceWeaveFrontend/src/features/graph/` |
| E — frontend workspace | Инспектор, редакторы, материалы, поиск, отчёты, настройки | Остальные назначенные feature-каталоги frontend |
| F — QA | Contract/E2E/security/performance-тесты и доказательства | `tests/`, выделенные тестовые каталоги, отчёт проверки |

Фактическое число агентов можно уменьшить. Независимо от количества одновременно работающих агентов один файл должен иметь одного владельца на текущий этап.

### 25.2. Правила совместной работы

Раздельные ветки/worktree на пакет работ. Агент не редактирует чужой working tree и не исправляет общие контракты «по пути». Изменение чужого файла предлагается через change request с конкретной причиной и тестом.

`Package.swift`, frontend `package.json`, lock-файлы, общий router, composition root и миграционный реестр изменяет только координатор после согласования зависимостей. Feature-агент добавляет отдельный route registrar; подключение регистратора выполняет владелец composition root.

Номера миграций выдаются централизованно. Уже принятая миграция не переписывается; добавляется следующая. Не разрешать двум агентам создать разные миграции с одним номером/именем.

### 25.3. Контракт задачи

Каждая задача содержит ID, цель, нормативные разделы, входные контракты, разрешённые файлы, запретные зоны, зависимости, ожидаемые артефакты, конкретные AC, команды проверки и критерий остановки.

Перед реализацией агент проверяет, что зависимость действительно готова. Нельзя заменить ещё не реализованный backend production-mock и отчитаться о готовом сквозном сценарии.

### 25.4. Отчёт агента

Агент сдаёт: перечень изменений; список изменённых файлов; команды реально выполненных тестов и результаты; непройденные проверки; миграции/новые зависимости; риски; инструкции запуска изменения.

Запрещено писать «всё работает», если запуск не выполнялся. Сборка и unit-тесты не доказывают автоматически работоспособность UI в Safari.

### 25.5. Изменение ТЗ

Допустимый повод: воспроизводимый блокер, конфликт требований, измеренная нехватка производительности или дефект безопасности. Недопустимый повод: привычка агента к другому framework.

Change request должен содержать минимальный пример проблемы, затронутые требования, варианты решения, влияние на сохранённые данные/API/сроки и предлагаемый тест. До принятия изменения исходное требование не считается отменённым.

Отсутствуют обязательные платные SaaS/API, секреты в Git, автоматически скачиваемые runtime-ассеты, непроверенные миграции production-базы и обещания готовности P1/P2. Все ограничения сообщаются явно.

## 28. Риски и запрещённые упрощения

| Риск / соблазн | Обязательная реакция |
|---|---|
| «Сделаем только красивый граф» | Первый инкремент должен сохранять реальный документ в backend и восстанавливать его после перезапуска |
| «Для интерактивности хватит HTML/CSS» | Использовать согласованный TypeScript frontend; не создавать статический макет вместо приложения |
| «На Rust привычнее агенту» | Это не блокер Swift; смена языка только через проверенный ADR |
| «Любой тип узла имеет только один файл» | Семантический тип и набор вложений независимы |
| «Выбор нового узла закрывает старый» | Раздельные состояния карточек и инспектора обязательны |
| «Свернём группу, заменив концы рёбер в БД» | Проекция только на frontend; оригинальные отношения неизменны |
| «Сохраним React Flow JSON целиком как базу» | Нужны независимая доменная модель, DTO и адаптер |
| «Хранить всё в localStorage быстрее» | Это не соответствует серверному хранению и переносимости |
| «На локальной другой БД тесты проходят, значит PostgreSQL готов» | Приёмочные транзакции, конкурентные повторы, FTS и backup/restore проверяются на настоящем PostgreSQL |
| «Достаточно скопировать каталог оригиналов» | Полная резервная копия включает согласованный дамп PostgreSQL и все оригиналы; восстановление проверяется совместно |
| «Последняя запись всегда побеждает» | Контроль ревизии и конфликт без тихой потери данных |
| «Для загрузки просто прочитаем весь файл» | Потоковый ввод/вывод и реальные проверки памяти |
| «Экспортируем только видимые/первые 200 узлов» | Состав определяется полным серверным набором и явным выбором |
| «Пересоберём старый отчёт по свежим данным» | Снимок неизменяем; актуализация создаёт новый снимок |
| «JSON Schema делает плагин безопасным» | Нужны проверки контекста/файлов; будущий запуск требует отдельной изоляции |
| «Контейнер = разрешение выполнить любой скрипт» | P0 не выполняет скрипты; P2 требует отдельной модели угроз |
| «Удалили привязку — удалим файл» | Сначала проверить все материалы, документы, корзину и снимки |
| «Проверки прошли, потому что код компилируется» | Требуются реальные integration/E2E/браузерные и негативные тесты |
| «Неизвестное поле импорта можно молча отбросить» | Версионирование и явная миграция/ошибка; отсутствие скрытой потери данных |

Начальные допущения, которые могут изменить объём, но **не блокируют старт по текущему ТЗ**: один пользователь, один граф на исследование, одноступенчатые группы, отсутствие трансляции медиа в другой кодек, desktop-first, отсутствие исполняемых плагинов. Изменение любого из них оформляется отдельной версией спецификации.
